# HTTP 连接管理

## 概述

### 是什么

平时说的"HTTP 支持长连接"，指的是 **TCP 连接复用（Keep-Alive / Persistent Connection）**：一条 TCP 连接上可以连续发送多个 HTTP 请求-响应，不必每次请求都重新建立连接。

**这和 SSE 不是一回事。** 两者处在不同层面：

- **HTTP 长连接**：省掉重复建立 TCP 连接的开销，属于**性能优化**，通信模型仍然是"一问一答"
- **SSE**：让服务端能主动往客户端推数据，属于**通信能力扩展**

SSE 和 WebSocket 反而是"用掉"了一条长连接——它们建立在长连接的能力之上，但目的完全不同。

### 解决什么问题

HTTP/1.0 时代每个请求都要独立建连：

```
短连接（HTTP/1.0 默认）:
  建连 → 请求1 → 响应1 → 断开
  建连 → 请求2 → 响应2 → 断开
  建连 → 请求3 → 响应3 → 断开
```

一个网页要加载 HTML、CSS、JS、几十张图片，就要重复几十次「三次握手 + 四次挥手」。握手本身要消耗一个 RTT（网络往返时延），HTTPS 还要再叠加 TLS 握手的 1~2 个 RTT。跨地域访问时 RTT 动辄几十上百毫秒，这部分开销远超实际传输数据的时间。

长连接把这些开销摊掉了：

```
长连接（HTTP/1.1 默认）:
  建连 → 请求1 → 响应1 → 请求2 → 响应2 → 请求3 → 响应3 → ... → 断开
```

除了省 RTT，还有一个容易被忽略的收益：**TCP 慢启动**。新建的 TCP 连接拥塞窗口很小，需要几个往返才能把带宽跑满。连接复用后，后续请求直接享受已经"热起来"的窗口。

## 核心概念

### Connection 头

长连接的开关就是请求/响应头里的 `Connection` 字段：

```http
GET /index.html HTTP/1.1
Host: example.com
Connection: keep-alive

HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1024
Connection: keep-alive
Keep-Alive: timeout=60, max=100
```

- **HTTP/1.1 默认开启长连接**，想关掉才需要显式写 `Connection: close`
- HTTP/1.0 默认关闭，需要显式写 `Connection: keep-alive`
- `Keep-Alive: timeout=60, max=100` 表示：空闲 60 秒后关闭，这条连接最多处理 100 个请求

注意 `Connection` 是**逐跳（hop-by-hop）头**，只在相邻两个节点之间有效。浏览器 → Nginx 是长连接，不代表 Nginx → 后端应用也是长连接，这两段要分别配置。

### 底层怎么划分消息边界

关键问题：一条 TCP 连接上连着发多个响应，接收方怎么知道第一个响应在哪结束、第二个从哪开始？

TCP 是**字节流**协议，本身没有"消息边界"的概念。所以 HTTP 必须自己在应用层划定边界，靠的是两种方式：

**1. `Content-Length`** —— 明确告诉对方响应体有多少字节，读满就是一条响应结束。

```http
HTTP/1.1 200 OK
Content-Length: 5

hello
```

**2. `Transfer-Encoding: chunked`** —— 响应体长度事先不确定（比如流式生成的内容），改用分块传输，每块前面写自己的长度，最后用一个长度为 0 的块表示结束。

```
HTTP/1.1 200 OK
Transfer-Encoding: chunked

5\r\n
hello\r\n
6\r\n
 world\r\n
0\r\n
\r\n          ← 长度为 0 的块 = 响应结束
```

**没有这两者之一，长连接就无法成立**——接收方只能靠"对方关闭连接"来判断响应结束，那自然就退化成短连接了。

## 几种"连接"方案的对比

| 方案 | 是否复用连接 | 谁能主动发消息 | 通信方向 |
|------|--------------|----------------|----------|
| HTTP Keep-Alive | 是 | 只有客户端 | 请求-响应 |
| 长轮询 (Long Polling) | — | 客户端发起，服务端 hold 住 | 模拟推送 |
| SSE | 是（占用一条） | 服务端 | 单向下行 |
| WebSocket | 是（升级后独占） | 双方 | 全双工 |

### 长轮询：用长连接模拟推送

在 SSE 普及前的常见做法：客户端发一个请求，服务端**不立即响应**，一直 hold 住直到有数据或超时，客户端收到响应后立刻再发下一个请求。

```
客户端 ──请求──> 服务端（挂起 30s...有数据了）
客户端 <─响应─── 服务端
客户端 ──请求──> 服务端（立刻再发一个）
```

它借用了长连接省下建连开销，但每推一条消息就要走完一轮请求-响应，开销仍然大于 SSE。

### SSE：一个永不结束的响应

SSE 的做法是**发起一个请求后，响应体永远不关闭**，服务端持续往这个流里写数据：

```http
GET /events HTTP/1.1

HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache

data: 消息1

data: 消息2
        ↑ 响应体一直不结束，服务端想推就写一段
```

本质是"一个超长的分块响应"，底层正是靠上面讲的 `Transfer-Encoding: chunked` 实现的——只是这个 chunked 流一直不发送结束块。

## [进阶] 深入理解

### 队头阻塞（Head-of-Line Blocking）

HTTP/1.1 的长连接有个限制：**同一条连接上，请求必须按顺序一个个来**。前一个响应没回完，后一个请求的响应就不能开始传（因为无法区分字节属于哪个响应）。

```
连接上：  请求1 → [响应1 很慢...] → 请求2 只能干等
```

浏览器的应对办法是**对同一个域名开 6~8 条并行连接**。这也是早年"域名分片"（把静态资源分散到 img1.xxx.com、img2.xxx.com）这类优化手段的由来。

HTTP/1.1 规范里其实定义过**管线化（Pipelining）**——允许不等响应就连着发多个请求——但因为响应仍须按序返回，队头阻塞没解决，且代理实现混乱，主流浏览器都已默认禁用。

### HTTP/2 与 HTTP/3 的解法

- **HTTP/2**：引入二进制分帧层，每个帧带 Stream ID，多个请求的帧可以在**一条连接上交错传输**，真正的多路复用。一个域名只需一条连接。但它仍跑在 TCP 上，某个包丢了会阻塞整条连接上的所有流——**TCP 层的队头阻塞**依然存在。
- **HTTP/3**：底层换成基于 UDP 的 QUIC，每个流独立处理丢包，彻底解决队头阻塞。

### 连接池

服务端之间调用（比如应用调数据库、调下游服务）通常用**连接池**来管理长连接：预先建好一批连接放池子里，用完归还而不是关闭。

需要关注的几个参数：

- **最大连接数**：超过后请求排队等待
- **空闲超时**：必须**小于**服务端和中间代理的 timeout，否则会拿到一条对方已单方面关闭的死连接
- **连接最大存活时间**：定期强制重建，避免后端扩容后流量始终打在老节点上

## [进阶] 最佳实践

### 常见坑点

- **客户端空闲超时 ≥ 服务端超时**：服务端已关闭连接，客户端还以为可用，复用时就报 `Connection reset` / `NoHttpResponseException`。经验做法是让客户端超时比服务端小几秒。
- **中间代理静默掐连接**：Nginx、云负载均衡通常有自己的空闲超时（常见 60s）。SSE / 长轮询这类长时间无数据的场景，要么调大代理超时，要么定期发心跳（SSE 用 `: ping` 注释行）。
- **响应被缓冲**：Nginx 默认会缓冲后端响应，导致 SSE 数据攒着不发。需要 `proxy_buffering off;`。
- **忘记读完响应体**：某些 HTTP 客户端里，如果不把响应体读完（或不 close），连接无法归还连接池，最终耗尽。

### 配置参考

Nginx 上游长连接（默认是短连接，必须显式配）：

```nginx
upstream backend {
    server 10.0.0.1:8080;
    keepalive 32;              # 每个 worker 保持的空闲长连接数
    keepalive_timeout 60s;
}

server {
    location / {
        proxy_pass http://backend;
        proxy_http_version 1.1;      # 必须，默认 1.0 不支持长连接
        proxy_set_header Connection "";  # 清掉逐跳头，否则会被透传
    }
}
```
