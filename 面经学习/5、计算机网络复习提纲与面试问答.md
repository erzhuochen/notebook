## 二、高频面试题

### 1. TCP 为什么需要三次握手？

回答：

TCP 三次握手主要是为了确认客户端和服务端双方的**发送能力**和**接收能力**都正常，同时同步双方的**初始序列号 ISN**，并避免历史连接请求导致服务端建立错误连接。

第一次握手，客户端发送 SYN，服务端可以确认客户端具备发送能力，服务端具备接收能力。第二次握手，服务端返回 SYN + ACK，客户端可以确认自己发送、接收正常，也能确认服务端发送、接收正常。第三次握手，客户端返回 ACK，服务端才能确认客户端具备接收能力。三次完成后，双方都确认了彼此的收发能力，并同步了后续可靠传输需要的初始序列号。

#### 追问 1：两次握手为什么不够？

回答：

两次握手不够，因为服务端发出 SYN + ACK 后，如果直接认为连接建立，就无法确认客户端是否真的收到了服务端的响应，也就无法确认客户端的**接收能力**。

另外，两次握手更容易受到**历史连接请求**影响。比如一个旧的 SYN 报文因为网络延迟后来才到达服务端，服务端如果只经过两次握手就建立连接，可能会为一个客户端并不想建立的连接分配资源，造成无效连接和资源浪费。

#### 追问 2：SYN Flood 是怎么利用半连接队列的？

回答：

SYN Flood 利用的是 TCP 三次握手中的半连接状态。攻击者大量发送 SYN 报文，服务端收到后会返回 SYN + ACK，并把这些连接放入**半连接队列**等待第三次 ACK。如果攻击者不返回 ACK，半连接队列就可能被占满，正常客户端的连接请求就无法被处理。

常见防御方式包括 **SYN Cookie**、调大半连接队列、缩短超时时间、高防 IP 或流量清洗。SYN Cookie 不是 HTTP Cookie，而是服务端把连接必要信息编码进 SYN + ACK 的初始序列号中，等客户端第三次握手返回 ACK 后再校验并创建连接，这样可以减少半连接队列被恶意占满的风险。

#### 追问 3：三次握手可以携带数据吗？

回答：

普通 TCP 下，第三次握手的 ACK 可以携带数据，因为此时客户端已经确认服务端的收发能力。第一次 SYN 通常不携带应用层数据，因为连接还没有建立完成。

不过 **TCP Fast Open** 是特殊情况，它允许客户端在 SYN 阶段携带数据，以减少一次 RTT，但需要客户端和服务端都支持，并且要配合 Cookie 机制防止重放等风险。

### 2. TCP 为什么需要四次挥手？

回答：

TCP 需要四次挥手，是因为 TCP 是**全双工通信**，客户端和服务端的发送方向需要分别关闭。一方发送 `FIN` 只能表示“我这边没有数据要发了”，但对方可能还有数据没有发送完，所以对方通常会先回复 `ACK`，等自己的数据也发送完后，再单独发送 `FIN`。

四次挥手的大致流程是：

1. 主动关闭方发送 `FIN=1, seq=x`，表示自己已经没有数据要发送了。
2. 被动关闭方收到后，返回 `ACK=1, ack=x+1`，表示已经收到关闭请求。此时被动关闭方可能还有数据要继续发送。
3. 被动关闭方发送完剩余数据后，再发送 `FIN=1, seq=y`，表示自己也没有数据要发送了。
4. 主动关闭方收到后，返回 `ACK=1, ack=y+1`，然后进入 **TIME_WAIT** 状态，等待一段时间后再真正关闭连接。

注意：挥手阶段用的是 **FIN**，不是 SYN。SYN 用于建立连接，FIN 用于关闭连接。第二次 ACK 和第三次 FIN 在某些情况下可以合并，比如被动关闭方已经没有数据要发送；但典型情况下会分开发，因为 ACK 表示“我收到了你的关闭请求”，FIN 表示“我这边也发送完了，可以关闭了”。

#### 追问 1：TIME_WAIT 是什么？

回答：

TIME_WAIT 是主动关闭方在发送第四次挥手的 ACK 后进入的状态。它不会立刻释放连接，而是等待 **2MSL** 左右的时间后再关闭。

这里的 MSL 是报文在网络中的最大生存时间。等待 2MSL 的目的，是**确保本次连接中的旧报文都从网络中消失**，并且如果最后一次 ACK 丢失，**主动关闭方还能收到对方重发的 FIN 并再次回复 ACK**。

#### 追问 2：为什么主动关闭方要进入 TIME_WAIT？

回答：

主动关闭方进入 TIME_WAIT 主要有两个原因。

第一，保证连接可以被**可靠关闭**。如果第四次挥手的 ACK 丢失，被动关闭方会因为收不到 ACK 而重发 FIN。主动关闭方处于 TIME_WAIT 时，还能收到这个 FIN 并重新发送 ACK。

第二，避免本次连接的**历史报文污染新连接**。如果旧连接的延迟报文还在网络中，而相同四元组很快被复用，新连接可能收到旧连接的残留报文。等待 2MSL 可以让旧报文尽量自然失效。

#### 追问 3：CLOSE_WAIT 过多通常说明什么问题？

回答：

CLOSE_WAIT 过多通常不是说明网络丢包率高，而是说明**被动关闭方的应用程序没有及时关闭连接**。

当一端收到对方的 FIN 后，会回复 ACK，并进入 CLOSE_WAIT 状态。接下来需要应用程序调用 `close()`，内核才会发送自己的 FIN，连接才会继续关闭。如果 CLOSE_WAIT 很多，通常说明程序已经知道对方要断开，但代码没有正确释放 socket，比如连接泄漏、线程阻塞、异常路径没有关闭连接，或者连接池使用不当。

### 3. TCP 如何保证可靠传输？

回答：

TCP 主要通过**序号、确认应答、校验和、重传机制、滑动窗口、流量控制和拥塞控制**来保证可靠传输。

首先，TCP 会给每个字节流编号，通过**序号**保证数据可以按正确顺序重组，也能识别重复数据。接收方收到数据后会返回 **ACK 确认应答**，告诉发送方自己已经收到了哪些数据。如果发送方长时间没有收到确认，就会触发**超时重传**；如果连续收到多个重复 ACK，也可以触发**快速重传**，不用等超时。

其次，TCP 通过**校验和**检查报文在传输过程中是否损坏。通过**滑动窗口**，发送方可以在没有收到前一个 ACK 的情况下连续发送多个报文，提高传输效率。通过**流量控制**，接收方用接收窗口 `rwnd` 告诉发送方自己还能接收多少数据，防止发送太快把接收方压垮。通过**拥塞控制**，发送方根据网络拥塞情况调整拥塞窗口 `cwnd`，避免把网络打满。

三次握手可以建立连接并同步初始序列号，四次挥手可以可靠关闭连接，但它们不是数据传输阶段保证可靠性的主要机制。

#### 追问 1：流量控制和拥塞控制有什么区别？

回答：

**流量控制**解决的是“发送方不要把接收方压垮”的问题，关注点是接收方的处理能力。接收方会在 TCP 报文中维护接收窗口 `rwnd`，告诉发送方自己还能接收多少数据，发送方不能发送超过接收窗口允许的数据量。

**拥塞控制**解决的是“发送方不要把网络压垮”的问题，关注点是整个网络链路的拥塞情况。发送方会维护拥塞窗口 `cwnd`，根据丢包、重复 ACK、RTT 等信号调整发送速率。常见策略包括**慢启动、拥塞避免、快重传、快恢复**。

实际发送窗口通常取 `rwnd` 和 `cwnd` 中较小的那个，即 `发送窗口 = min(rwnd, cwnd)`。

#### 追问 2：滑动窗口解决了什么问题？

回答：

滑动窗口主要解决两个问题：一是提升传输效率，二是配合流量控制限制发送速度。

如果没有滑动窗口，TCP 只能发送一个报文后等待 ACK，再发送下一个报文，这种“停等模式”效率很低。滑动窗口允许发送方在窗口范围内连续发送多个尚未确认的数据，提高网络吞吐量。

同时，接收方可以通过接收窗口告诉发送方自己还能接收多少数据，窗口越小，发送方能连续发送的数据越少；窗口为 0 时，发送方需要暂停发送普通数据，避免接收方处理不过来。

#### 追问 3：什么是快重传？

回答：

快重传是 TCP 在不等待超时的情况下，尽快重传丢失报文的一种机制。

当接收方发现中间某个报文丢失，但后面的报文到了，它会反复发送同一个 ACK，表示“我还在等这个序号开始的数据”。发送方如果连续收到 **3 个重复 ACK**，就会判断对应的数据段大概率丢失，于是立即重传这个数据段，而不是等到超时重传。

快重传通常会配合**快恢复**使用：发送方会把慢启动阈值 `ssthresh` 调低，一般设为当前拥塞窗口的一半，然后调整拥塞窗口，避免因为一次丢包就完全回到最慢的慢启动初始状态。
