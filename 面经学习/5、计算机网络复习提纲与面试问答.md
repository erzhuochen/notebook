## 二、高频面试题

### 1. TCP 为什么需要三次握手？

回答：

TCP 三次握手主要是为了确认客户端和服务端双方的**发送能力**和**接收能力**都正常，同时同步双方的**初始序列号 ISN**，并避免历史连接请求导致服务端建立错误连接。

第一次握手，客户端发送 SYN，服务端可以确认客户端具备发送能力，服务端具备接收能力。第二次握手，服务端返回 SYN + ACK，客户端可以确认自己发送、接收正常，也能确认服务端发送、接收正常。第三次握手，客户端返回 ACK，服务端才能确认客户端具备接收能力。三次完成后，双方都确认了彼此的收发能力，并同步了后续可靠传输需要的初始序列号。

#### 追问 1：两次握手为什么不够？

回答：

两次握手不够，因为服务端发出 SYN + ACK 后，如果直接认为连接建立，就无法确认客户端是否真的收到了服务端的响应，也就无法确认客户端的**接收能力**。

另外，两次握手更容易受到**历史连接请求**影响。比如一个旧的 SYN 报文因为网络延迟后来才到达服务端，服务端如果只经过两次握手就建立连接，可能会为一个客户端并不想建立的连接分配资源，造成无效连接和资源浪费。

#### 追问 2：SYN Flood 是怎么利用半连接队列的？

回答：

SYN Flood 利用的是 TCP 三次握手中的半连接状态。攻击者大量发送 SYN 报文，服务端收到后会返回 SYN + ACK，并把这些连接放入**半连接队列**等待第三次 ACK。如果攻击者不返回 ACK，半连接队列就可能被占满，正常客户端的连接请求就无法被处理。

常见防御方式包括 **SYN Cookie**、调大半连接队列、缩短超时时间、高防 IP 或流量清洗。SYN Cookie 不是 HTTP Cookie，而是服务端把连接必要信息编码进 SYN + ACK 的初始序列号中，等客户端第三次握手返回 ACK 后再校验并创建连接，这样可以减少半连接队列被恶意占满的风险。

#### 追问 3：三次握手可以携带数据吗？

回答：

普通 TCP 下，第三次握手的 ACK 可以携带数据，因为此时客户端已经确认服务端的收发能力。第一次 SYN 通常不携带应用层数据，因为连接还没有建立完成。

不过 **TCP Fast Open** 是特殊情况，它允许客户端在 SYN 阶段携带数据，以减少一次 RTT，但需要客户端和服务端都支持，并且要配合 Cookie 机制防止重放等风险。

### 2. TCP 为什么需要四次挥手？

回答：

TCP 需要四次挥手，是因为 TCP 是**全双工通信**，客户端和服务端的发送方向需要分别关闭。一方发送 `FIN` 只能表示“我这边没有数据要发了”，但对方可能还有数据没有发送完，所以对方通常会先回复 `ACK`，等自己的数据也发送完后，再单独发送 `FIN`。

四次挥手的大致流程是：

1. 主动关闭方发送 `FIN=1, seq=x`，表示自己已经没有数据要发送了。
2. 被动关闭方收到后，返回 `ACK=1, ack=x+1`，表示已经收到关闭请求。此时被动关闭方可能还有数据要继续发送。
3. 被动关闭方发送完剩余数据后，再发送 `FIN=1, seq=y`，表示自己也没有数据要发送了。
4. 主动关闭方收到后，返回 `ACK=1, ack=y+1`，然后进入 **TIME_WAIT** 状态，等待一段时间后再真正关闭连接。

注意：挥手阶段用的是 **FIN**，不是 SYN。SYN 用于建立连接，FIN 用于关闭连接。第二次 ACK 和第三次 FIN 在某些情况下可以合并，比如被动关闭方已经没有数据要发送；但典型情况下会分开发，因为 ACK 表示“我收到了你的关闭请求”，FIN 表示“我这边也发送完了，可以关闭了”。

#### 追问 1：TIME_WAIT 是什么？

回答：

TIME_WAIT 是主动关闭方在发送第四次挥手的 ACK 后进入的状态。它不会立刻释放连接，而是等待 **2MSL** 左右的时间后再关闭。

这里的 MSL 是报文在网络中的最大生存时间。等待 2MSL 的目的，是**确保本次连接中的旧报文都从网络中消失**，并且如果最后一次 ACK 丢失，**主动关闭方还能收到对方重发的 FIN 并再次回复 ACK**。

#### 追问 2：为什么主动关闭方要进入 TIME_WAIT？

回答：

主动关闭方进入 TIME_WAIT 主要有两个原因。

第一，保证连接可以被**可靠关闭**。如果第四次挥手的 ACK 丢失，被动关闭方会因为收不到 ACK 而重发 FIN。主动关闭方处于 TIME_WAIT 时，还能收到这个 FIN 并重新发送 ACK。

第二，避免本次连接的**历史报文污染新连接**。如果旧连接的延迟报文还在网络中，而相同四元组很快被复用，新连接可能收到旧连接的残留报文。等待 2MSL 可以让旧报文尽量自然失效。

#### 追问 3：CLOSE_WAIT 过多通常说明什么问题？

回答：

CLOSE_WAIT 过多通常不是说明网络丢包率高，而是说明**被动关闭方的应用程序没有及时关闭连接**。

当一端收到对方的 FIN 后，会回复 ACK，并进入 CLOSE_WAIT 状态。接下来需要应用程序调用 `close()`，内核才会发送自己的 FIN，连接才会继续关闭。如果 CLOSE_WAIT 很多，通常说明程序已经知道对方要断开，但代码没有正确释放 socket，比如连接泄漏、线程阻塞、异常路径没有关闭连接，或者连接池使用不当。

### 3. TCP 如何保证可靠传输？

回答：

TCP 主要通过**序号、确认应答、校验和、重传机制、滑动窗口、流量控制和拥塞控制**来保证可靠传输。

首先，TCP 会给每个字节流编号，通过**序号**保证数据可以按正确顺序重组，也能识别重复数据。接收方收到数据后会返回 **ACK 确认应答**，告诉发送方自己已经收到了哪些数据。如果发送方长时间没有收到确认，就会触发**超时重传**；如果连续收到多个重复 ACK，也可以触发**快速重传**，不用等超时。

其次，TCP 通过**校验和**检查报文在传输过程中是否损坏。通过**滑动窗口**，发送方可以在没有收到前一个 ACK 的情况下连续发送多个报文，提高传输效率。通过**流量控制**，接收方用接收窗口 `rwnd` 告诉发送方自己还能接收多少数据，防止发送太快把接收方压垮。通过**拥塞控制**，发送方根据网络拥塞情况调整拥塞窗口 `cwnd`，避免把网络打满。

三次握手可以建立连接并同步初始序列号，四次挥手可以可靠关闭连接，但它们不是数据传输阶段保证可靠性的主要机制。

#### 追问 1：流量控制和拥塞控制有什么区别？

回答：

**流量控制**解决的是“发送方不要把接收方压垮”的问题，关注点是接收方的处理能力。接收方会在 TCP 报文中维护接收窗口 `rwnd`，告诉发送方自己还能接收多少数据，发送方不能发送超过接收窗口允许的数据量。

**拥塞控制**解决的是“发送方不要把网络压垮”的问题，关注点是整个网络链路的拥塞情况。发送方会维护拥塞窗口 `cwnd`，根据丢包、重复 ACK、RTT 等信号调整发送速率。常见策略包括**慢启动、拥塞避免、快重传、快恢复**。

实际发送窗口通常取 `rwnd` 和 `cwnd` 中较小的那个，即 `发送窗口 = min(rwnd, cwnd)`。

#### 追问 2：滑动窗口解决了什么问题？

回答：

滑动窗口主要解决两个问题：一是提升传输效率，二是配合流量控制限制发送速度。

如果没有滑动窗口，TCP 只能发送一个报文后等待 ACK，再发送下一个报文，这种“停等模式”效率很低。滑动窗口允许发送方在窗口范围内连续发送多个尚未确认的数据，提高网络吞吐量。

同时，接收方可以通过接收窗口告诉发送方自己还能接收多少数据，窗口越小，发送方能连续发送的数据越少；窗口为 0 时，发送方需要暂停发送普通数据，避免接收方处理不过来。

#### 追问 3：什么是快重传？

回答：

快重传是 TCP 在不等待超时的情况下，尽快重传丢失报文的一种机制。

当接收方发现中间某个报文丢失，但后面的报文到了，它会反复发送同一个 ACK，表示“我还在等这个序号开始的数据”。发送方如果连续收到 **3 个重复 ACK**，就会判断对应的数据段大概率丢失，于是立即重传这个数据段，而不是等到超时重传。

快重传通常会配合**快恢复**使用：发送方会把慢启动阈值 `ssthresh` 调低，一般设为当前拥塞窗口的一半，然后调整拥塞窗口，避免因为一次丢包就完全回到最慢的慢启动初始状态。

### 4. HTTP/1.1、HTTP/2、HTTP/3 有什么区别？

回答：

HTTP/1.1、HTTP/2、HTTP/3 的核心区别主要体现在**连接复用方式、队头阻塞、传输层协议、头部压缩和建连效率**上。

**HTTP/1.1** 默认支持长连接，可以在一个 TCP 连接上复用多个请求，减少频繁建连的成本。但 HTTP/1.1 的请求和响应整体上仍然按顺序处理，容易出现**应用层队头阻塞**：前面的响应没回来，后面的响应就可能被卡住。虽然有管线化机制，但实际使用很少。

**HTTP/2** 基于 TCP，引入二进制帧、Stream、多路复用和 **HPACK** 头部压缩。多个请求可以拆成帧，在同一个 TCP 连接中并发传输，解决了 HTTP/1.1 层面的队头阻塞。但因为底层仍然是 TCP，如果某个 TCP 报文丢失，TCP 必须按序交付，整个连接上的所有 Stream 都会等待这个丢失报文重传，所以 HTTP/2 仍然存在 **TCP 层队头阻塞**。

**HTTP/3** 基于 QUIC，而 QUIC 基于 UDP 实现可靠传输、拥塞控制、多路复用和 TLS 1.3 加密。QUIC 在传输层就支持多个独立 Stream，某个 Stream 丢包时，通常只阻塞这个 Stream，不会阻塞其他 Stream，因此解决了 TCP 层队头阻塞问题。HTTP/3 使用 **Connection ID** 标识连接，即使客户端从 Wi-Fi 切到 4G，IP 或端口变化了，也可以继续识别同一个连接。HTTP/3 使用 **QPACK** 做头部压缩，首连通常可以做到 1-RTT，连接恢复时可以利用会话票据等信息实现 0-RTT，但 0-RTT 有重放风险，通常只适合幂等请求。

#### 追问 1：HTTP/2 为什么仍然有队头阻塞？

回答：

HTTP/2 的多路复用解决的是 HTTP 应用层的队头阻塞，但它底层仍然运行在 **TCP** 上。TCP 要保证字节流**按序交付**，如果某个 TCP 报文丢失，即使其他 Stream 的数据已经到达，TCP 也不能把后面的字节交给上层应用，必须等待丢失的报文重传成功。

所以 HTTP/2 中某个 Stream 对应的 TCP 包丢失时，可能会阻塞整个 TCP 连接上的所有 Stream，这就是 HTTP/2 仍然存在的 **TCP 层队头阻塞**。

#### 追问 2：QUIC 为什么能连接迁移？

回答：

QUIC 能连接迁移，是因为它不只依赖传统 TCP 的四元组来识别连接，而是使用 **Connection ID** 标识连接。

TCP 连接通常由源 IP、源端口、目标 IP、目标端口这个四元组确定。如果客户端从 Wi-Fi 切换到 4G，IP 或端口变化，原来的 TCP 连接就失效了。QUIC 把连接身份和 IP、端口解耦，只要客户端后续报文携带的 Connection ID 能被服务端识别，服务端就可以把它当成同一个连接继续处理，从而支持网络切换后的连接迁移。

#### 追问 3：HTTP/3 为什么使用 QPACK 而不是 HPACK？

回答：

HTTP/3 使用 QPACK，是因为 HTTP/2 的 **HPACK** 强依赖 TCP 的有序传输，而 HTTP/3/QUIC 的多个 Stream 是相互独立传输的，不能让头部压缩机制重新制造严重的队头阻塞。

HPACK 使用动态表压缩请求头，编码端和解码端必须按同样顺序更新动态表。在 HTTP/2 中，TCP 保证字节流有序，所以动态表状态比较容易保持一致。但在 HTTP/3 中，不同 Stream 可以独立到达。如果仍然照搬 HPACK，一个 Stream 依赖的动态表更新还没到，后续很多 Stream 都可能被卡住。

QPACK 为 QUIC 重新设计了头部压缩机制，通过独立的单向控制流同步动态表更新，并允许发送方在必要时选择不引用尚未确认的动态表项，改用字面量或更安全的编码方式。这样既能压缩头部，又能减少因为动态表不同步造成的阻塞。

### 5. HTTPS 比 HTTP 多了什么？

回答：

HTTPS 可以理解为 **HTTP + TLS**。HTTP 本身是明文传输，别人如果能截获网络包，就可能看到你访问了什么、提交了什么数据，甚至篡改响应内容。HTTPS 在 HTTP 和传输层之间加了一层 TLS，主要多了三种能力：**加密、身份认证、完整性校验**。

**加密**解决的是“别人看不懂”的问题。比如你登录网站时提交用户名和密码，如果是 HTTP，中间网络设备理论上可以看到明文；如果是 HTTPS，中间人即使抓到包，也只能看到加密后的数据。

**身份认证**解决的是“我到底连的是不是目标服务器”的问题。比如你访问 `https://bank.com`，浏览器不能只看对方说“我是 bank.com”，而要通过证书验证它是否真的拥有 `bank.com` 对应的合法身份。否则中间人可以自己伪造一个服务器骗你连接。

**完整性校验**解决的是“数据有没有被篡改”的问题。比如服务端返回“转账金额 100 元”，中间人不能把它悄悄改成“10000 元”还不被发现。TLS 会通过认证加密或消息认证机制发现篡改。

以现代常见的 **ECDHE** 握手为例，客户端和服务端不只是交换椭圆曲线公钥份额，还会各自生成一个随机数。客户端生成 **ClientRandom**，再生成临时椭圆曲线私钥 `a`，发出公钥份额 `G*a`；服务端生成 **ServerRandom**，再生成临时椭圆曲线私钥 `b`，发出公钥份额 `G*b`，并用证书对应的私钥对握手信息做签名。客户端验证证书和签名后，双方都能算出同一个共享秘密，例如 `G*a*b`。

但 `G*a*b` 通常不会直接作为“对称加密私钥”。更准确地说，**ECDHE 负责协商共享秘密，ClientRandom 和 ServerRandom 负责提供本次会话的新鲜性**，最后再把共享秘密、两个随机数以及握手上下文一起送进密钥派生函数，生成真正用于后续通信的**会话密钥**。

可以粗略理解为：

```text
共享秘密 = ECDHE(G*a, G*b)
会话密钥 = KDF(共享秘密, ClientRandom, ServerRandom, 握手上下文)
```

这样做的好处是：即使两次连接访问的是同一个网站，双方证书也一样，每次握手生成的临时私钥和随机数都不同，最终派生出的会话密钥也会不同。两个随机数不只是“增加复杂度”，更重要的是保证**每次连接的新鲜性**，降低重放、预计算等风险。

#### 追问 1：HTTPS 一定安全吗？

回答：

HTTPS 不等于“绝对安全”。它主要保护的是**传输过程**，也就是尽量保证你和目标服务器之间的数据不被窃听、不被篡改、目标身份可信。但它不能解决所有安全问题。

举几个例子：

1. 如果你访问的是钓鱼域名，比如真正的银行是 `bank.com`，但你访问了 `bank-login-example.com`，这个钓鱼网站也可以申请自己的 HTTPS 证书。浏览器小锁只能说明“你和这个钓鱼域名之间的连接是加密的”，不能说明这个网站本身可信。
2. 如果网站后端本身被入侵，HTTPS 也没法保护你。因为数据到了服务端之后已经被解密，服务端内部怎么处理属于应用安全问题。
3. 如果网页存在 XSS、CSRF、SQL 注入等漏洞，HTTPS 也不能直接修复这些业务漏洞。
4. 如果用户电脑被安装了恶意根证书，或者公司代理主动做 HTTPS 解密代理，浏览器可能会信任被代理重新签发的证书，这时传输也可能被中间设备看到。

另外，老式的 **RSA 密钥交换**确实有一个问题：如果攻击者之前保存了密文流量，并且后来拿到了服务器私钥，就可能解密过去的会话。现代 TLS 更常用 **ECDHE**，它的临时密钥每次会话都会重新生成，用完就丢。服务器证书私钥主要用于签名认证，不直接决定过去会话的加密密钥，所以即使服务器私钥后来泄露，也很难反推出过去会话的密钥，这叫**前向安全**。

#### 追问 2：证书是如何防止中间人攻击的？

回答：

证书的核心作用是把**域名**和**服务器公钥**绑定起来，并让这个绑定关系由受信任的 CA 背书。

可以这样理解：如果服务端只是直接发给浏览器一个公钥，中间人也可以拦截请求，然后把自己的公钥发给浏览器。浏览器如果没有办法判断“这个公钥到底是不是 bank.com 的”，就可能和中间人建立加密连接。这样中间人再和真正的服务器建立另一条连接，就能夹在中间偷看或篡改数据。

证书解决这个问题的方式是：

1. 服务器把自己的域名、公钥、有效期、用途等信息提交给 CA。
2. CA 审核通过后，会对证书内容做哈希，然后用 **CA 私钥**对哈希结果签名。
3. 浏览器拿到服务器证书后，会用 **CA 公钥**验证签名。如果证书内容被篡改，哈希就对不上，签名验证会失败。
4. 浏览器还会检查证书域名是否匹配、是否过期、用途是否正确、是否被吊销，以及证书链能不能一路验证到受信任的根 CA。

比如你访问 `https://bank.com`，中间人如果想冒充银行，就必须拿出一个对 `bank.com` 有效、并且由可信 CA 签发的证书。它自己随便生成的证书，浏览器不会信；它即使转发银行的真证书，也没有银行证书对应的私钥，无法完成后续签名认证，所以也冒充不了真正的服务器。

注意：根 CA 证书通常内置在操作系统或浏览器的**信任根证书库**里，不是“运行时从中间 CA 获取”。根 CA 不是数学意义上的绝对可信，而是浏览器和操作系统预先选择信任它。

#### 追问 3：对称加密和非对称加密分别用在哪里？

回答：

HTTPS 里可以粗略理解为：**非对称加密/签名负责身份认证和密钥协商，对称加密负责真正的数据传输**。

为什么这样分工？因为对称加密速度快，适合加密大量 HTTP 数据；非对称算法计算成本高，不适合拿来加密每一个请求和响应。比如你下载一个 100MB 文件，如果全程用非对称加密，性能会很差；而用 AES-GCM 或 ChaCha20-Poly1305 这样的对称加密算法，就高效得多。

在老式 RSA 密钥交换里，可以说“客户端生成一个对称密钥，然后用服务器证书里的公钥加密发给服务端，服务端用私钥解密得到这个对称密钥”。但在现代更常见的 **ECDHE** 中，不是直接把对称密钥传过去，而是客户端和服务端各自生成临时密钥参数，双方通过数学计算得到同一个共享秘密，再派生出会话密钥。

所以更准确的表达是：

- **非对称部分**：用于证书签名验证、服务端身份认证，以及 ECDHE 这类密钥协商过程。
- **对称部分**：握手完成后，用派生出来的会话密钥加密真正的 HTTP 请求和响应。

一个简单例子：你和服务器先通过非对称机制确认“对方真的是我要找的人”，再一起协商出一个只有你们俩知道的临时暗号。之后真正聊天时，不再每句话都用复杂的非对称算法，而是用这个临时暗号进行快速加密通信。

### 6. TLS 握手大致过程是什么？

回答：

TLS 握手的目标可以先记成一句话：**客户端和服务端先确认身份，再协商出后续对称加密要用的会话密钥**。真正的 HTTP 数据不会在握手阶段直接明文传输，而是在握手完成后用会话密钥加密传输。

以常见的 **ECDHE** 握手为例，可以按下面的顺序理解：

1. 客户端发送 `ClientHello`。里面通常包含客户端随机数 `ClientRandom`、支持的 TLS 版本、支持的加密套件、支持的椭圆曲线类型等信息。可以理解为客户端先说：“我支持这些加密方式，你选一个我们都能用的。”
2. 服务端返回 `ServerHello`，选择双方都支持的 TLS 版本和加密套件，并发送服务端随机数 `ServerRandom`。服务端还会发送自己的证书，用来证明“我确实是这个域名对应的服务器”。
3. 双方进行 ECDHE 密钥协商。客户端生成临时私钥 `a` 和公钥份额 `G*a`，服务端生成临时私钥 `b` 和公钥份额 `G*b`。双方交换公钥份额后，客户端可以用 `a` 和 `G*b` 算出共享秘密，服务端可以用 `b` 和 `G*a` 算出同一个共享秘密，本质上都能得到类似 `G*a*b` 的结果。
4. 服务端会用证书对应的私钥对握手关键内容做**数字签名**，客户端用证书里的公钥验签。这里要注意：服务端的 `G*b` 不是“用服务器私钥加密”，客户端也不是“用服务器公钥解密”；更准确地说，是服务端用私钥**签名**，客户端用公钥**验证签名**，防止中间人篡改密钥交换参数。
5. 双方把 `ClientRandom`、`ServerRandom` 和 ECDHE 算出的共享秘密交给密钥派生函数，生成真正用于后续通信的**会话密钥**。后续 HTTP 请求和响应就用这个会话密钥进行对称加密。
6. 最后双方会发送 `Finished` 消息，验证前面的握手内容没有被篡改。如果验证通过，TLS 握手完成，后续就开始传输加密的 HTTP 数据。

可以用一个生活例子理解：客户端和服务端先交换“支持哪些暗号规则”，服务端拿出身份证明自己是谁，然后双方各自拿出一部分临时材料，组合出一个只有双方能算出来的临时暗号。之后真正聊天时，就用这个临时暗号快速加密。

#### 追问 1：RSA 握手和 ECDHE 握手有什么区别？

回答：

RSA 握手和 ECDHE 握手最大的区别在于：**RSA 密钥交换依赖服务器长期私钥来保护会话密钥，ECDHE 使用临时密钥协商出会话密钥**。

在老式 RSA 密钥交换中，客户端会生成一个预主密钥，然后用服务器证书里的公钥加密后发给服务端。服务端用自己的私钥解密，得到预主密钥，再派生出会话密钥。问题是，如果攻击者提前保存了这些加密流量，后来又拿到了服务器私钥，就可能解密出过去的预主密钥，进而还原过去的会话内容。

在 ECDHE 中，客户端和服务端每次连接都会生成临时的椭圆曲线私钥，比如 `a` 和 `b`。这些临时私钥通常用完就丢，服务器证书私钥主要用来做身份认证和签名，不直接用来解密会话密钥。所以即使服务器长期私钥以后泄露，攻击者也很难反推出过去每次连接中临时生成的 `a` 或 `b`，因此过去的通信内容仍然更安全。

一个类比：RSA 像是每次都把临时密码锁进“服务器长期保险箱”里，只要以后保险箱钥匙泄露，过去锁进去的密码都有风险；ECDHE 像是双方现场用一次性材料调出一个临时密码，材料用完就销毁，之后就算服务器身份证钥匙泄露，也很难还原过去的临时密码。

#### 追问 2：什么是前向安全？

回答：

**前向安全**指的是：即使服务器的长期私钥在未来某一天泄露，攻击者也不能解密过去已经发生过的通信内容。

重点是“未来泄露，不影响过去”。比如攻击者今天抓包保存了你和服务器之间的 HTTPS 流量，但它当时没有密钥。一个月后，服务器证书私钥不幸泄露。如果使用的是不具备前向安全的 RSA 密钥交换，过去抓到的流量可能有被解密的风险；如果使用的是 ECDHE，由于每次会话使用的临时密钥已经销毁，攻击者只有服务器长期私钥，也很难推导出过去的会话密钥。

所以前向安全保护的是**历史会话**。它不能保证服务器私钥泄露之后的新连接仍然安全；一旦发现长期私钥泄露，证书仍然需要吊销和更换。

#### 追问 3：TLS 1.3 为什么更快？

回答：

TLS 1.3 更快，主要是因为它**简化了握手流程**，删除了很多旧算法，并且让客户端在第一次 `ClientHello` 里就带上密钥协商需要的 `key_share`。

在 TLS 1.2 中，完整握手通常需要更多往返：客户端先告诉服务端自己支持什么，服务端选择参数并返回证书和密钥交换信息，客户端再继续发送自己的密钥交换信息，之后双方才能确认会话密钥。可以理解为双方先来回商量规则，再开始真正凑密钥。

在 TLS 1.3 中，客户端第一次发 `ClientHello` 时，就会带上自己支持的加密套件、椭圆曲线组，以及一个或多个主流曲线的 `key_share`。如果服务端支持客户端带来的参数，就可以直接返回自己的 `key_share`，双方在 **1-RTT** 内完成密钥协商。也就是说，少了一些“你支持什么、我再发参数”的来回确认。

如果客户端猜的曲线服务端不支持，服务端会返回 `HelloRetryRequest` 让客户端重发合适的 `key_share`，这时会多一次往返。但正常情况下，客户端会优先带常见曲线，所以大多数连接可以更快完成。

TLS 1.3 还支持会话恢复时的 **0-RTT**：如果客户端之前和服务端连接过，保存了恢复信息，下次可以在第一个请求里就带上早期数据。不过 0-RTT 有重放风险，所以通常只适合 GET、HEAD 这类幂等请求，不适合转账、下单这种不能重复执行的请求。

### 7. Cookie、Session、Token 有什么区别？

回答：

这三个概念容易混在一起，最好先分清层次：**Cookie 是一种浏览器存储和自动携带数据的机制；Session 和 Token 是两种常见的登录态方案**。

**Cookie** 保存在客户端，也就是浏览器本地。服务端可以通过响应头 `Set-Cookie` 让浏览器保存一段数据，之后浏览器访问同一个域名时，会自动把符合条件的 Cookie 放到请求头里带给服务端。Cookie 可以存登录凭证，也可以存语言偏好、主题设置、购物车标识等，所以 Cookie 本身不是登录方案，只是一个“浏览器帮你保存并自动携带小数据”的机制。

举个例子：你登录网站后，服务端返回 `Set-Cookie: sessionId=abc123`。浏览器保存这个 Cookie，以后你访问这个网站的订单页，浏览器会自动带上 `sessionId=abc123`。服务端看到这个值，就知道你是谁。

**Session** 是服务端保存用户会话状态的一种方案。通常浏览器本地只保存一个 `sessionId`，真正的用户信息、登录状态、权限信息保存在服务端，比如 JVM 内存、Redis、数据库中。服务端收到请求后，根据 `sessionId` 去服务端存储里查用户状态。

Session 的特点是：状态在服务端，服务端控制能力强，比如可以随时让某个用户下线；但缺点是服务端要存储状态，机器多了之后要考虑共享 Session。

**Token** 是客户端携带访问凭证的一种方案。服务端登录成功后签发一个 Token，客户端之后每次请求都带上这个 Token，服务端校验它是否合法。Token 可以是不透明字符串，也可以是 JWT。

这里要注意：Token 不一定是“加密保存在本地”。很多 JWT 默认只是 **Base64URL 编码 + 签名**，它的内容可以被客户端解码看到，只是不能被篡改。签名的作用是防止别人改内容，比如把 `userId=1` 改成 `userId=2`。如果真的不想让客户端看到内容，需要额外做加密，比如 JWE，但普通 JWT 更多是签名，不是加密。

可以用一句话总结：

- **Cookie**：浏览器存储和自动携带数据的机制。
- **Session**：服务端保存状态，客户端通常只保存 `sessionId`。
- **Token**：客户端保存访问凭证，服务端通过签名、查询或规则校验凭证是否合法。

#### 追问 1：JWT 的优缺点是什么？

回答：

JWT 的优点是**无状态、易扩展、适合前后端分离和跨服务传递身份信息**。

JWT 里面通常包含 Header、Payload、Signature 三部分。Payload 可以放一些用户身份信息，比如 `userId`、角色、过期时间。服务端校验签名正确，就能确认这个 Token 没被篡改。这样服务端不一定需要保存每个用户的登录状态，多个服务只要共享签名密钥或公钥，就能识别用户身份。

举个例子：用户登录后拿到 JWT，请求订单服务、购物车服务、用户服务时都带上这个 JWT。各个服务只要能验证签名，就知道这是哪个用户，不一定每次都去登录服务查 Session。

JWT 的缺点也很明显：**一旦签发，在过期前很难主动失效**。比如用户改密码、账号被封禁、管理员强制下线，如果服务端完全不保存状态，那么已经签发出去的 JWT 在过期前仍然可能被使用。

常见解决思路有几种：

1. **缩短 Access Token 有效期**，比如 15 分钟，再配合 Refresh Token 续期。这样即使 Token 泄露，风险窗口也比较短。
2. **黑名单机制**：Redis 只保存已经失效或被封禁的 Token 标识，比如 `jti`。请求进来时，除了验签，还查一下是否在黑名单里。优点是存储量相对小，缺点是又引入了服务端状态。（？）
3. **白名单机制**：Redis 保存当前仍然有效的 Token 或会话。优点是控制力强，缺点是更接近 Session，服务端存储压力更大。
4. **Token 版本号**：在用户表或 Redis 里保存一个版本号，JWT 里也带版本号。用户改密码或封禁时提升版本号，旧 Token 就失效。

所以 JWT 不是“永远比 Session 好”。如果业务很重视强制下线和权限实时变更，就不能只靠纯无状态 JWT。

#### 追问 2：Token 放 Cookie 还是 LocalStorage？

回答：

Token 放 Cookie 还是 LocalStorage，没有绝对答案，核心要看你更想防哪类风险：**XSS** 还是 **CSRF**。

如果 Token 放在 **LocalStorage**，前端 JavaScript 读取很方便，可以手动放到请求头里，比如 `Authorization: Bearer xxx`。这种方式常见于前后端分离应用。但缺点是：一旦页面出现 XSS 漏洞，攻击者的 JavaScript 就可以直接读取 LocalStorage，把 Token 偷走。

如果 Token 放在 **Cookie**，浏览器会自动携带。配合 `HttpOnly` 后，JavaScript 不能直接读取这个 Cookie，能降低 XSS 直接偷 Token 的风险。但 Cookie 会自动随请求发送，所以要注意 CSRF。可以通过 `SameSite=Lax/Strict`、CSRF Token、校验 Origin/Referer 等方式防护。

举个例子：

- 放 LocalStorage：像是你把门禁卡放在桌面上，自己拿很方便，但如果有人通过 XSS 进了你的房间，也容易直接拿走。
- 放 HttpOnly Cookie：像是门禁卡锁在一个小盒子里，普通 JS 拿不到，但浏览器会自动帮你刷卡，所以要防止别人诱导浏览器去刷不该刷的门。

实践中常见选择：

1. 如果是浏览器 Web 应用，比较推荐把敏感 Token 放在 **HttpOnly + Secure + SameSite** 的 Cookie 中，再配合 CSRF 防护。
2. 如果必须放在 LocalStorage，要非常重视 XSS 防护，比如严格输出转义、CSP、避免把不可信内容插入 HTML。
3. 如果是 App、小程序、服务端调用服务端接口，就不一定受浏览器 Cookie 机制限制，可以放在各自平台更合适的安全存储中。

一句话总结：LocalStorage 怕 **XSS 偷 Token**；Cookie 怕 **CSRF 自动带凭证**，但 `HttpOnly` Cookie 能降低 Token 被 JS 直接读取的风险。

#### 追问 3：分布式 Session 怎么做？

回答：

分布式 Session 的问题来自多台服务器。单机时，Session 可以存在本机内存里；但如果有三台服务器 A、B、C，用户第一次请求打到 A，Session 存在 A 内存里，第二次请求打到 B，B 就找不到这个 Session 了。

常见方案有几种：

1. **Session 复制**：服务器之间互相同步 Session。优点是改动小，缺点是机器多了之后同步成本高，不适合大规模集群。
2. **粘性会话**：负载均衡器把同一个用户固定转发到同一台服务器。优点是简单，缺点是服务器宕机后 Session 容易丢，也不利于均衡流量。
3. **集中式 Session 存储**：把 Session 放到 Redis、数据库等共享存储里。最常见的是 Redis。所有服务器收到 `sessionId` 后，都去 Redis 查询 Session。优点是多台服务器共享登录态，易扩展；缺点是 Redis 成为关键依赖，需要考虑高可用、过期时间和容量。
4. **改用 Token/JWT**：把登录态从服务端 Session 转成客户端 Token。优点是服务端状态少，扩展方便；缺点是主动失效、权限实时变更会更复杂。

实际 Java 后端里最常见的是 **Redis 存 Session**。流程可以理解为：浏览器 Cookie 里保存 `sessionId`，请求到任意一台应用服务器后，服务器拿这个 `sessionId` 去 Redis 查用户信息。这样用户请求打到哪台机器都能识别身份。
