## 四、高频面试题

### 1. JVM 运行时数据区有哪些？ **【重点】**

回答：

JVM 运行时数据区可以理解为：Java 程序运行时，JVM 把不同类型的数据放到不同区域里管理。主要包括 **程序计数器、Java 虚拟机栈、本地方法栈、Java 堆、方法区**。

按线程是否共享来分：

- **线程私有**：程序计数器、Java 虚拟机栈、本地方法栈。
- **线程共享**：Java 堆、方法区。

每个区域负责的事情不同：

1. **程序计数器**：记录当前线程执行到哪一条字节码指令。因为线程切换后要恢复执行位置，所以每个线程都要有自己的程序计数器。
2. **Java 虚拟机栈**：保存 Java 方法调用过程中的栈帧。每次方法调用都会创建一个栈帧，里面有局部变量表、操作数栈、动态链接、方法返回地址等。
3. **本地方法栈**：服务 native 方法，也就是 Java 调用 C/C++ 等本地方法时使用的栈。
4. **Java 堆**：主要存放对象实例，是垃圾回收最主要管理的区域。平时说的 GC，大多数时候重点就是堆。
5. **方法区**：存放类元信息、运行时常量池、字段和方法信息、静态变量等。方法区是 JVM 规范里的逻辑概念，HotSpot 在不同版本中有不同实现。

另外，**直接内存**不属于 JVM 运行时数据区的一部分，但经常和 JVM 内存一起讨论。比如 NIO 的 `DirectByteBuffer` 会使用堆外内存，如果使用不当，也可能出现 `Direct buffer memory` 相关 OOM。

可以用一个例子理解：执行 `User user = new User()` 时，`user` 这个引用变量通常在当前线程的栈帧局部变量表里，真正的 `User` 对象在堆里，`User` 类的字段、方法、类元信息在方法区/元空间里，当前线程执行到哪条指令由程序计数器记录。

#### 追问 1：哪些区域是线程私有的，哪些是线程共享的？

回答：

**线程私有**的区域有三个：程序计数器、Java 虚拟机栈、本地方法栈。

它们之所以线程私有，是因为每个线程都有自己的执行路径。比如线程 A 正在执行 `methodA()`，线程 B 正在执行 `methodB()`，它们的方法调用栈、局部变量、当前执行位置都不同，不能混在一起。

**线程共享**的区域主要有两个：Java 堆、方法区。

堆是线程共享的，因为对象通常要被多个线程访问。比如一个 Spring 单例 Bean 放在堆里，多个请求线程都可能调用它的方法。方法区也是共享的，因为类元信息对整个 JVM 进程是公共的，同一个类不需要给每个线程各存一份。

总结：

- **线程私有**：程序计数器、虚拟机栈、本地方法栈。
- **线程共享**：堆、方法区。
- **常一起讨论但不属于运行时数据区**：直接内存。

#### 追问 2：为什么程序计数器不会发生 OOM？

回答：

程序计数器不会发生 OOM，主要是因为它占用的内存非常小，只是记录当前线程正在执行的字节码指令地址或执行位置，而且 JVM 规范中没有规定程序计数器会抛出 `OutOfMemoryError`。

它不像堆那样要不断存放新对象，也不像栈那样会随着方法递归不断压入栈帧。程序计数器只是每个线程维护一个很小的执行位置记录。

举个例子：线程执行一段字节码时，程序计数器类似“书签”，记录读到哪一行。线程被 CPU 切走后，下次恢复执行时，根据这个“书签”继续往下执行。书签本身很小，不会像书架那样因为书太多而塞满。

需要注意：程序计数器“不 OOM”不是因为它完全不占内存，而是因为它占用极小，并且规范中它是唯一一个没有规定 OOM 情况的运行时数据区。

#### 追问 3：方法区、永久代、元空间是什么关系？

回答：

**方法区**是 JVM 规范中的逻辑概念，规定这里要存放类元信息、运行时常量池、静态变量、方法信息等数据。**永久代**和**元空间**是 HotSpot 虚拟机对方法区的不同实现方式。

可以这样理解：方法区像接口规范，永久代和元空间是具体实现类。

在 HotSpot 中：

1. **JDK 7 及以前**：方法区主要用永久代实现。永久代在 JVM 管理的内存里，大小通常受 `-XX:PermSize`、`-XX:MaxPermSize` 影响。
2. **JDK 7**：字符串常量池从永久代移到了堆中。这一点不是 JDK 8 才发生。
3. **JDK 8 及以后**：永久代被移除，类元信息放到**元空间 Metaspace**。元空间使用的是本地内存，也就是 native memory，大小可通过 `-XX:MetaspaceSize`、`-XX:MaxMetaspaceSize` 控制。

为什么要从永久代改成元空间？一个重要原因是永久代大小比较难估计，容易因为加载类太多导致 `PermGen space` OOM。元空间使用本地内存，默认上限更灵活，但如果类加载失控，比如大量动态生成代理类、频繁创建类加载器，也仍然可能出现 `Metaspace` OOM。

总结：

- **方法区**：JVM 规范中的逻辑区域。
- **永久代**：HotSpot JDK 8 之前对方法区的实现。
- **元空间**：HotSpot JDK 8 之后对方法区的实现，使用本地内存。
- **字符串常量池**：JDK 7 起已经移到堆中。

### 2. JVM 中常见的内存溢出异常有哪些？ **【重点】**

回答：

JVM 中常见的内存相关异常可以分成几类：**堆溢出、GC 开销过大、元空间溢出、栈溢出、无法创建本地线程、直接内存溢出**。

常见形式包括：

1. **`java.lang.OutOfMemoryError: Java heap space`**  
   堆内存不足。通常是对象太多、对象太大，或者对象本来应该被回收但仍然被引用，导致 GC 回收不掉。

2. **`java.lang.OutOfMemoryError: GC overhead limit exceeded`**  
   GC 开销过大。JVM 花了大量时间做 GC，但只回收了很少内存。可以理解为 JVM 一直在拼命打扫房间，但房间几乎腾不出空间，程序已经接近不可用。

3. **`java.lang.OutOfMemoryError: Metaspace`**  
   元空间不足。通常和类加载过多有关，比如大量动态代理类、CGLIB 生成类、反射生成类、频繁创建类加载器且无法回收。

4. **`java.lang.StackOverflowError`**  
   栈溢出。注意它是 `Error`，但不是 `OutOfMemoryError`。常见原因是递归太深、方法调用链过长，导致虚拟机栈里的栈帧太多。

5. **`java.lang.OutOfMemoryError: unable to create new native thread`**  
   无法创建新的本地线程。通常不是 Java 堆满了，而是系统层面线程资源不足，比如线程数太多、每个线程栈占用太大、操作系统线程数限制或内存限制。

6. **`java.lang.OutOfMemoryError: Direct buffer memory`**  
   直接内存不足。常见于 NIO、Netty、堆外内存使用较多的场景。直接内存不在 Java 堆里，但仍然占用进程的本地内存。

可以用例子区分：如果代码不断 `new byte[1024 * 1024]` 并放到 List 里，可能是 **Java heap space**；如果无限递归调用自己，可能是 **StackOverflowError**；如果不断用 CGLIB 动态生成新类，可能是 **Metaspace**；如果不断创建线程，可能是 **unable to create new native thread**。

总结关键词：

- **堆 OOM**：对象太多或泄漏。
- **GC overhead**：GC 很频繁但效果很差。
- **Metaspace**：类加载太多或类加载器泄漏。
- **StackOverflowError**：调用栈太深。
- **unable to create new native thread**：线程资源不足。
- **Direct buffer memory**：堆外直接内存不足。

#### 追问 1：Java heap space 通常是什么原因？

回答：

`Java heap space` 表示 Java 堆空间不足。核心原因是：**堆里存活对象占用的空间超过了堆可用容量，GC 之后仍然腾不出足够空间**。

常见原因有两类：

1. **对象确实太多或太大**  
   比如一次性从数据库查出几百万条数据放进 List，或者读取一个超大文件直接加载到内存里。这种情况不一定是内存泄漏，而是程序设计本身需要太多内存。

2. **内存泄漏**  
   对象已经不再需要，但仍然被某些引用链持有，GC 无法回收。比如静态 Map 不断缓存用户对象但不清理，监听器注册后不注销，ThreadLocal 用完不 remove。

排查时不能只看“堆满了”，还要判断是**内存确实不够**还是**对象泄漏**。常见思路是查看 GC 日志和堆 dump，分析哪些对象占用最多、它们被谁引用。

例子：如果接口每次请求都把结果放进一个全局 `static List`，这个 List 会越来越大，即使请求结束，对象仍然被静态变量引用，GC 回收不了，最终可能出现 `Java heap space`。


#### 追问 2：StackOverflowError 和栈 OOM 有什么区别？

回答：

`StackOverflowError` 和栈相关的 `OutOfMemoryError` 都和线程栈有关，但原因不同。

**`StackOverflowError`** 表示单个线程的调用栈深度超过了栈容量。最常见原因是递归太深或死递归。每调用一次方法，虚拟机栈中就会压入一个栈帧；递归一直不结束，栈帧越来越多，最终把当前线程的栈撑爆。

例子：

```java
void f() {
    f();
}
```

这段代码会不断调用自己，每次调用都产生一个新栈帧，最终触发 `StackOverflowError`。

**栈 OOM** 通常指无法为线程分配新的栈空间，常见表现是 `OutOfMemoryError: unable to create new native thread`。它不一定是某个线程调用太深，而可能是线程数量太多，每个线程都需要一块栈内存，系统无法再创建新线程。

例子：程序不断 `new Thread().start()`，每个线程都不退出，线程越来越多，操作系统线程资源或本地内存被耗尽，最终可能报 `unable to create new native thread`。

区别可以这样记：

- **StackOverflowError**：一个线程的调用栈太深。
- **unable to create new native thread**：线程太多，系统分不出新的线程栈或线程资源。

#### 追问 3：Metaspace OOM 通常是什么原因？

回答：

`Metaspace OOM` 表示元空间不足。元空间主要存放**类元信息**，比如类名、字段、方法、运行时常量池、方法字节码相关元数据等。它使用的是本地内存，不在 Java 堆里。

常见原因不是简单“项目类太多”，而是**类加载数量持续增长，或者类加载器无法被回收**。

典型场景：

1. **大量动态生成类**  
   比如 CGLIB、Javassist、ByteBuddy、动态代理、表达式引擎频繁生成新类。如果生成的类越来越多，元空间会持续增长。

2. **类加载器泄漏**  
   在热部署、插件化、脚本引擎场景中，如果旧的 ClassLoader 本该被回收，但仍然被线程、静态变量、缓存引用，就会导致它加载过的类也无法卸载。

3. **应用本身加载类过多**  
   比如依赖非常多，或者启动时扫描、生成了大量类，也可能推高元空间使用。

举个例子：某个服务每次执行规则都用 CGLIB 生成一个新类，而且把生成类的 Class 对象放进静态 Map 里不清理。运行时间越久，元空间里的类元信息越多，最终可能出现 `OutOfMemoryError: Metaspace`。

排查时可以关注：类加载数量是否持续增长、是否有大量动态生成类、是否存在 ClassLoader 泄漏，以及 `-XX:MaxMetaspaceSize` 是否设置过小。

### 3. 栈帧是什么？ **【重点】**

回答：

**栈帧**是 Java 虚拟机栈中的基本单位，用来保存一次方法调用所需要的运行时数据。可以先记住一句话：**每调用一个方法，JVM 就会在线程的虚拟机栈里创建一个栈帧；方法执行完，这个栈帧就会出栈**。

一个栈帧通常包含四类核心信息：**局部变量表、操作数栈、动态链接、方法返回地址**。

举个例子：

```java
int add(int a, int b) {
    int c = a + b;
    return c;
}
```

当线程执行 `add(1, 2)` 时，JVM 会为 `add` 方法创建一个栈帧。参数 `a`、`b` 和局部变量 `c` 会放在局部变量表相关位置；计算 `a + b` 时，中间操作会用到操作数栈；方法执行完后，JVM 根据返回地址回到调用 `add` 的地方继续执行。

栈帧是线程私有的，因为每个线程都有自己的方法调用链。线程 A 调用 `add()` 和线程 B 调用 `add()`，会分别在各自的虚拟机栈里创建栈帧，不会共用同一个栈帧。

#### 追问 1：一个方法调用对应几个栈帧？

回答：

一次方法调用对应一个栈帧。方法被调用时，栈帧入栈；方法执行完成、正常返回或异常退出时，栈帧出栈。

比如：

```java
void a() {
    b();
}

void b() {
    c();
}

void c() {
}
```

如果当前线程执行 `a()`，调用链是 `a -> b -> c`。执行到 `c()` 时，虚拟机栈中大致会有三个栈帧：`a` 的栈帧、`b` 的栈帧、`c` 的栈帧。`c()` 执行完后，`c` 的栈帧出栈，回到 `b()`；`b()` 执行完后，`b` 的栈帧出栈，回到 `a()`。

所以递归调用时，即使调用的是同一个方法，每调用一次也会创建一个新的栈帧。

#### 追问 2：局部变量表、操作数栈、动态链接、返回地址分别有什么作用？

回答：

栈帧里的几个组成部分可以这样理解：

1. **局部变量表**  
   存放方法参数和方法内部定义的局部变量。比如实例方法里的 `this`、方法参数 `a`、`b`，以及局部变量 `c`，都会放在局部变量表中。基本类型直接存值；引用类型存的是对象引用，对象本体通常在堆里。

2. **操作数栈**  
   JVM 执行字节码时用来临时存放操作数和中间计算结果。比如计算 `a + b` 时，JVM 会把 `a` 和 `b` 压入操作数栈，然后执行加法指令，弹出两个数并把结果压回操作数栈。

   可以把操作数栈理解成计算草稿纸。局部变量表像“固定编号的格子”，操作数栈像“临时计算区”。

3. **动态链接**  
   每个栈帧中都有一个指向运行时常量池中该方法所属类的引用，用来支持方法调用过程中的符号引用解析。class 文件里很多方法、字段最初是以**符号引用**形式存在的，比如“调用哪个类的哪个方法”。运行时需要把这些符号引用解析或关联到实际的方法、字段引用，这个过程和动态链接有关。

   注意：动态链接不是把“变量字面量转换成真实对象”。更准确地说，它和**符号引用到直接引用**、方法调用定位有关。

4. **方法返回地址**  
   方法执行完后，JVM 需要知道回到哪里继续执行。方法返回地址记录的就是**调用者接下来要执行的位置**。比如 `b()` 调用 `c()`，`c()` 执行完后，要回到 `b()` 中调用 `c()` 后面的那条指令。

   注意：方法返回地址不是“返回值的地址”。返回值本身可能通过操作数栈等方式传递给调用者，而返回地址表示控制流回到哪里。

#### 追问 3：递归为什么容易导致 StackOverflowError？

回答：

递归容易导致 `StackOverflowError`，是因为**每递归调用一次方法，都会创建一个新的栈帧并压入当前线程的虚拟机栈**。

比如：

```java
void f(int n) {
    f(n + 1);
}
```

这个方法没有递归出口，每次调用 `f()` 都会再调用一次 `f()`。第一次调用创建一个栈帧，第二次调用又创建一个新的栈帧，第三次再创建一个。栈帧不断累积，但没有机会出栈，最终超过当前线程栈的最大容量，就会触发 `StackOverflowError`。

即使有递归出口，如果递归层数太深，也可能栈溢出。比如递归处理一个非常深的链表或树结构，深度达到几十万层，虽然逻辑上有出口，但调用链太长，仍然可能把栈撑满。

解决思路通常包括：

- 确保递归有正确的终止条件。
- 控制递归深度。
- 将深递归改成循环或显式栈。
- 必要时调整线程栈大小，比如 `-Xss`，但这只是缓解，不是根本解决逻辑问题。

关键词：**一次方法调用一个栈帧，递归越深栈帧越多，超过线程栈容量就 StackOverflowError**。

### 4. 对象是如何分配内存的？ **【重点】**

回答：

Java 对象的内存分配，通常可以先按这个主线理解：**大多数普通对象会优先在堆的新生代 Eden 区分配；如果对象存活时间较长，经过多次 Minor GC 后可能晋升到老年代；特殊情况下，大对象可能直接进入老年代；如果逃逸分析成功，对象也可能不真正分配到堆上**。

典型流程：

1. 代码执行 `new Object()`，JVM 先判断这个对象需要多少内存。
2. 如果开启了 TLAB，并且当前线程的 TLAB 空间够用，就优先在当前线程的 TLAB 中分配。
3. 如果 TLAB 不够，或者对象不能在 TLAB 中分配，就在 Eden 区尝试分配。
4. 如果 Eden 区空间不足，会触发 Minor GC。
5. Minor GC 后，如果对象仍然存活，会被复制到 Survivor 区，年龄增加；年龄达到阈值后，或者 Survivor 空间放不下时，可能晋升到老年代。
6. 如果对象很大，JVM 可能直接把它分配到老年代，避免在新生代来回复制。

这里要注意：对象年龄通常记录在对象头的 **Mark Word** 中，但不是“每发生一次 GC，所有对象年龄都 +1”。更准确地说，**对象在 Minor GC 后仍然存活，并在新生代的 Survivor 区之间复制时，年龄会增加**。如果年龄达到阈值，比如常见默认最大年龄是 15，或者触发动态年龄判断，就可能进入老年代。

还要注意，现代 JVM 有逃逸分析。如果 JVM 判断一个对象不会逃出当前方法或当前线程，可能进行**栈上分配**或**标量替换**。这时从结果看，这个对象不一定真的以完整对象形式分配到堆上。

例子：一个请求里创建的临时 `StringBuilder`，方法执行完就不用了，这类对象大概率在 Eden 中很快被回收；而一个全局缓存 Map 里的对象长期被引用，经过多次 GC 后可能进入老年代。

#### 追问 1：对象优先分配在 Eden 区是什么意思？

回答：

对象优先分配在 Eden 区，意思是：**大多数新创建的普通对象，会先放到新生代的 Eden 区，而不是一开始就放到老年代**。

这么设计的原因来自一个经验规律：**大多数对象朝生夕死**。也就是说，很多对象刚创建不久就没用了。比如一次接口请求里创建的临时 DTO、临时字符串、局部集合对象，往往请求结束后就可以回收。

新生代 GC，也就是 Minor GC，通常只回收新生代，成本比 Full GC 低很多。如果新对象先放 Eden，那么大量短命对象可以在 Eden 中被快速回收，不需要进入老年代。

可以类比成垃圾分类：Eden 像一个临时垃圾桶，大量短期垃圾先放这里，清理频率高；老年代像长期仓库，只放那些确实存活很久的对象。如果一开始就把所有东西放长期仓库，仓库会很快变乱，清理成本也更高。

典型过程：

1. 新对象进入 Eden。
2. Eden 满了，触发 Minor GC。
3. 已经不可达的对象被回收。
4. 仍然存活的对象被复制到 Survivor 区。
5. 存活多轮后，才可能晋升到老年代。

#### 追问 2：大对象为什么可能直接进入老年代？

回答：

大对象可能直接进入老年代，主要是为了避免在新生代中发生大量复制成本和空间压力。

大对象通常指需要一大块连续内存的对象，比如超大的数组：

```java
byte[] data = new byte[50 * 1024 * 1024];
```

如果这个对象先放 Eden，可能马上把 Eden 占满，触发 Minor GC。更麻烦的是，Minor GC 使用复制算法时，存活对象需要从 Eden 复制到 Survivor。如果大对象在新生代中来回复制，成本很高，而且 Survivor 区可能根本放不下。

所以 JVM 可能根据参数和收集器策略，把特别大的对象直接分配到老年代。这样可以避免大对象在新生代中反复复制。

但这也有风险：如果大对象很多，老年代会很快被占满，可能触发 Full GC。比如一次性读取很多大文件到内存，或者频繁创建大数组，都可能给老年代带来压力。

总结：**大对象直接进老年代，是为了减少新生代复制成本；但大对象过多会增加老年代压力**。

#### 追问 3：TLAB 是什么，为什么能减少分配竞争？

回答：

TLAB 是 **Thread Local Allocation Buffer**，线程本地分配缓冲区。它是 Eden 区里给每个线程预先划出的一小块私有分配区域。

对象分配本质上是在堆里申请一块内存。如果多个线程同时在 Eden 区分配对象，就可能竞争同一个分配指针。为了保证线程安全，JVM 需要使用 CAS 或加锁来更新分配指针，这会带来开销。

有了 TLAB 后，每个线程优先在自己的 TLAB 中分配对象。因为这块区域只属于当前线程，所以线程在里面分配对象时不需要和其他线程竞争。只有当 TLAB 用完，线程需要申请新的 TLAB，或者对象太大无法放进 TLAB 时，才需要走更慢的全局分配路径。

例子：假设 Eden 是一整块大空地，多个线程都要来摆摊。如果大家都抢同一个入口位置，就会排队和冲突。TLAB 相当于先给每个线程划一个小摊位，线程在自己的摊位里摆东西，不需要每次都去公共入口抢位置。

总结：

- **TLAB 位于 Eden 区**。
- **每个线程优先在自己的 TLAB 中分配对象**。
- **TLAB 减少了多线程同时分配对象时的 CAS 或锁竞争**。
- **TLAB 空间不够或对象太大时，仍可能走普通 Eden 分配或老年代分配**。

### 5. 如何判断对象可以被回收？ **【重点】**

回答：

JVM 主流判断对象是否可以被回收，使用的是**可达性分析算法**。核心思路是：从一组称为 **GC Roots** 的根对象出发，沿着对象之间的引用链往下搜索；如果某个对象从 GC Roots 出发无法到达，就说明它已经不再被程序的“活跃部分”使用，具备被 GC 回收的条件。

这里要注意两个表述：

1. 不是“没有被遍历到就一定马上回收”，而是**不可达对象具备回收条件**。具体什么时候回收，要看 GC 是否发生、采用什么收集器、对象是否有特殊处理逻辑等。
2. 可达性分析判断的是对象和 GC Roots 之间是否存在引用链。只要有一条引用链能从 GC Roots 到达这个对象，它就不能被当作垃圾回收。

举个例子：

```java
static User cachedUser;

void test() {
    User u = new User();
    cachedUser = u;
}
```

`test()` 方法结束后，局部变量 `u` 消失了，但 `cachedUser` 是静态变量，仍然引用着这个 `User` 对象。静态变量可以作为 GC Roots 相关引用链的一部分，所以这个对象仍然可达，不能回收。

再看另一个例子：

```java
void test() {
    User u = new User();
}
```

方法结束后，如果没有其他地方引用这个 `User` 对象，那么从 GC Roots 出发就找不到它，它就变成不可达对象，之后 GC 发生时可以回收。

关键词：**GC Roots、引用链、可达对象不可回收、不可达对象具备回收条件**。

#### 追问 1：引用计数法有什么问题？

回答：

引用计数法的思路很直观：每个对象维护一个计数器，有一个地方引用它，计数器就加 1；引用失效，计数器就减 1；计数器为 0，就说明没有引用指向它，可以回收。

它的问题是：**很难解决循环引用**。

例子：

```java
class Node {
    Node next;
}

Node a = new Node();
Node b = new Node();
a.next = b;
b.next = a;

a = null;
b = null;
```

这时从程序外部已经访问不到 `a` 和 `b` 原来指向的两个对象了，它们应该可以被回收。但它们内部互相引用：对象 A 引用对象 B，对象 B 又引用对象 A。如果使用引用计数法，它们的引用计数都不是 0，就可能无法被回收。

可达性分析能解决这个问题，因为它不是看对象之间有没有互相引用，而是看它们能不能从 GC Roots 出发被访问到。上面例子里，虽然两个对象互相引用，但从 GC Roots 出发已经到不了它们，所以它们仍然可以被回收。

总结：

- **引用计数法**：实现简单，判断快，但循环引用难处理。
- **可达性分析**：从 GC Roots 出发判断对象是否还和程序活跃部分相连，是 JVM 主流 GC 使用的判断方式。

#### 追问 2：可达性分析算法是什么？

回答：

可达性分析算法是 JVM 判断对象是否存活的主流算法。它的过程是：**从 GC Roots 出发，沿着引用关系向下搜索，所有能被搜索到的对象都是可达对象；搜索不到的对象就是不可达对象，具备被回收的条件**。

可以把内存里的对象看成一张图。对象是图中的节点，对象之间的引用是边。GC Roots 是图的起点。GC 做的事情类似从这些起点开始做图遍历。

例子：

```text
GC Roots -> A -> B -> C

D -> E
E -> D
```

从 GC Roots 出发，可以到达 A、B、C，所以 A、B、C 是可达对象，不能回收。D 和 E 虽然互相引用，但从 GC Roots 出发到不了它们，所以 D 和 E 是不可达对象，可以被回收。

这个算法的关键点是：**对象自己互相引用不代表一定存活；必须能从 GC Roots 出发被访问到，才算存活**。

#### 追问 3：哪些对象可以作为 GC Roots？

回答：

常见可以作为 GC Roots 的对象包括：

1. **虚拟机栈中引用的对象**  
   比如当前正在执行的方法里的局部变量、方法参数引用的对象。

   例子：

   ```java
   void test() {
       User user = new User();
   }
   ```

   当 `test()` 正在执行时，局部变量 `user` 在当前线程栈帧里，它引用的 `User` 对象就是可达的。

2. **方法区中类静态属性引用的对象**  
   比如 `static Map<String, Object> cache` 引用的缓存对象。

3. **方法区中常量引用的对象**  
   比如字符串常量池中的某些引用，或者运行时常量池中仍然被使用的常量引用。这里不能简单写成“final 常量都是 GC Roots”，更准确是**常量引用的对象**可能成为 GC Roots 相关引用链的一部分。

4. **本地方法栈中 JNI 引用的对象**  
   如果 native 方法持有了 Java 对象引用，这些对象也可能作为 GC Roots 的可达起点。

5. **被 synchronized 持有锁的对象**  
   正在被线程持有 monitor 锁的对象也不能随便回收。

6. **JVM 内部引用的对象**  
   比如系统类加载器、基本数据类型对应的 Class 对象、常驻异常对象等 JVM 内部需要使用的对象。

面试里常用的简化版可以这样答：

- **栈中引用的对象**
- **静态变量引用的对象**
- **常量引用的对象**
- **被锁持有的对象**

- **JNI 引用的对象**
- **JVM 内部使用的对象**

### 6. Java 有哪些引用类型？ **【重点】**

回答：
- 强引用：不会被GC回收。
- 软引用：当内存不够时，会在GC时被回收（具体时机由JVM决定），且将软引用放入配置的队列中
- 弱引用：在GC时会被回收
- 虚引用：虚引用用 `PhantomReference` 表示，不能通过 `get()` 获取对象，必须配合 ReferenceQueue 使用，主要用于跟踪对象被回收的时机，常见于堆外资源清理。

#### 追问 1：强引用、软引用、弱引用、虚引用分别适合什么场景？

回答：
- 强引用：强引用适合**普通业务对象**，只要还在使用，就不希望 GC 回收。
- 软引用：软引用适合**内存敏感缓存**，比如图片缓存、临时计算结果缓存。内存充足时可以保留，内存紧张时允许 GC 回收，之后需要时再重新加载。
- 弱引用：弱引用适合**不希望影响对象生命周期**的场景，比如 ThreadLocalMap 的 key、WeakHashMap 的 key。当外部强引用消失后，弱引用不会阻止对象被回收。
- 虚引用：虚引用适合做对象回收后的通知和资源清理，不能通过它获取对象本身，通常要和 ReferenceQueue 配合使用。

#### 追问 2：ThreadLocal 为什么和弱引用有关？

回答：
ThreadLocalMap 的 Entry 中，key 是 ThreadLocal 的弱引用，value 是强引用。
这样设计是为了避免 ThreadLocal 对象本身因为 ThreadLocalMap 的 key 而无法回收。假如外部已经没有强引用指向某个 ThreadLocal，GC 后这个 key 会被清掉，变成 null。
但问题是，key 被清掉后，value 仍然被 Entry 强引用着。只要线程还活着，ThreadLocalMap 还在，这个 value 就可能一直留在内存里，尤其在线程池中更明显。
所以 ThreadLocal 用完后要调用 remove，最好写在 finally 中，避免 value 残留和线程复用导致的数据污染。

#### 追问 3：软引用适合做缓存吗？

回答：
软引用可以用来做内存敏感缓存，但不推荐作为业务缓存的首选方案。

它适合缓存一些可重新加载、丢失也没关系的数据。比如图片、临时计算结果。内存充足时对象可能保留，内存紧张时 JVM 可以回收这些只被软引用关联的对象。

但软引用缓存有一个问题：回收时机不够可控。JVM 什么时候清理软引用，业务代码很难精确控制，可能导致缓存命中率不稳定。

如果使用 `Map<String, SoftReference<Object>>`，还需要配合 ReferenceQueue 清理已经失效的引用。实际删除 Map 项时，最好让 SoftReference 自己记录 key，否则从队列里取到引用后，不容易知道该删除哪个 key。

实际项目中，如果要做本地缓存，更推荐使用 Caffeine 或 Guava Cache，通过最大容量、过期时间和淘汰策略来控制缓存。
