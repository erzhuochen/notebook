## 3 分钟项目介绍

下面这版适合校招或初级岗位。它使用“重点学习和分析”措辞，不虚构个人开发经历。如果某部分确实由你亲自实现，可以据实改成“我负责”；不要把阅读源码说成独立完成项目。

> 我重点学习和分析的项目是旗鱼直播，它是一个仿斗鱼的教学型直播后端，基于 Java 17、Spring Boot 3 和 Spring Cloud Alibaba。项目按微服务拆分为用户、账户、直播间、礼物、钱包、消息和 IM 等模块。普通 HTTP 请求先经过 Spring Cloud Gateway，由网关完成路由和 token 认证，再进入聚合 API；API 通过 Dubbo 调用各领域 provider。Nacos负责服务注册发现和外部配置，Kafka负责异步解耦和削峰，Redis承担缓存、登录状态、在线用户、IM 路由、余额、红包和库存等多种状态，MySQL保存核心业务数据。
>
> 我重点掌握了两条链路。第一条是 IM 群聊。浏览器通过 WebSocket 连接 Netty IM Core，登录后 IM 本机保存用户 Channel，Redis保存用户连接的 IM 实例地址。聊天业务包先发到 Kafka，msg-provider 查询直播间 Redis Set 得到在线用户，Router 按用户绑定的 IM 地址分组，再通过 Dubbo 自定义 Cluster 定向调用正确的 IM 实例，最后写回目标 Channel。这条链路让我理解了长连接服务为什么不能随机负载均衡，以及心跳、ACK、重连和集群路由的关系。
>
> 第二条是送礼和秒杀。送礼接口把带业务标识的消息写入 Kafka，由消费者完成余额校验扣减和礼物推送，用消息队列吸收峰值。秒杀库存先从 MySQL 预热到 Redis，再用 Lua原子完成库存检查和扣减，创建待支付订单，超时后回滚库存。
>
> 我也对源码做了生产化评审。当前送礼只用短 TTL Redis key 去重，余额扣减后用本地线程池异步写库；库存回滚使用 Kafka 加本地 DelayQueue。这些属于教学实现，遇到消息重投或服务重启仍有一致性风险。我的改进思路是使用稳定业务幂等键、数据库唯一流水、订单状态 CAS、Outbox 或可靠消息、可恢复的延迟任务和定时对账。这样既能保留 Kafka 和 Redis 的吞吐优势，又能让资金和库存状态可追踪、可重试、可补偿。

## 30～45 分钟模拟面试流程

执行规则：

1. 一次只看一道题，先口述再展开答案提示。
2. 基础题控制在 60～90 秒，项目链路题控制在 2 分钟。
3. 每题按 0～5 分评分：结论 1 分、流程 2 分、边界 1 分、改进 1 分。
4. 回答中主动使用“当前源码”和“生产改进”，但不要机械重复。
5. 总分 70 分以上合格；任何资金、库存、消息题出现“绝不重复、绝不丢、强一致”且无条件说明，该题最多 2 分。

## 第一轮：项目架构与微服务

### 问题 1：请介绍项目整体架构

答题关键词：

```text
Gateway -> API -> Dubbo provider
WebSocket -> IM Core -> Kafka -> msg-provider -> Router -> IM Core
Nacos / Redis / Kafka / MySQL
当前源码与教学边界
```

追问：为什么需要聚合 API，而不是前端直接调用所有 provider？

回答思路：统一 HTTP 契约、登录上下文和服务编排；provider 保持领域能力；减少前端理解内部微服务拓扑。API 也不能演变成所有业务逻辑的大泥球。

### 问题 2：HTTP、Dubbo、Kafka、WebSocket 分别用在哪？

标准摘要：

- HTTP：浏览器请求 Gateway/API，请求响应。
- Dubbo：服务间同步 RPC，需要立即拿结果。
- Kafka：异步解耦、削峰和事件通知，接受最终一致性。
- WebSocket：客户端与 IM 的双向长连接和主动推送。

追问：送礼为什么不用全同步 Dubbo？

回答思路：扣款、查在线用户和广播链路长，高峰会把 HTTP 线程和下游打满；Kafka吸收峰值，但需要异步结果和可靠性设计。

### 问题 3：Nacos 在项目中做什么？

答题关键词：

```text
注册中心：实例注册、发现、健康状态
配置中心：按 application name 导入 yml
Namespace/Group/Data ID
Nacos 提供实例，不执行 RPC
```

追问：Nacos 挂了，已有 Dubbo 调用一定立刻失败吗？

回答思路：不一定，取决于 Dubbo 本地实例列表缓存、已建立连接、配置和故障持续时间；新实例变化和长期恢复会受影响。

### 问题 4：Dubbo 一次调用经过什么过程？

答题关键词：

```text
@DubboReference 代理
服务发现
负载均衡
序列化和网络请求
@DubboService provider
反序列化结果
```

追问：写接口为什么要谨慎配置重试？

回答思路：provider 可能已经成功但响应丢失，重试会重复扣款/建单；先有稳定幂等键和去重状态。

## 第二轮：Gateway、用户和缓存

### 问题 5：讲一下项目登录鉴权链路

闭卷调用链：

```text
qytk Cookie
-> AccountCheckFilter
-> IAccountTokenRPC
-> AccountTokenRpcImpl/AccountTokenServiceImpl
-> Redis token:userId
-> qiyu_gh_user_id Header
-> QiyuUserInfoInterceptor
-> QiyuRequestContext
```

追问：当前最明显的三个问题是什么？

回答思路：失败返回 `Mono.empty()`；同步 RPC 拖慢 Gateway；内部 Header 防伪造边界；ThreadLocal 异常清理。

### 问题 6：项目如何处理缓存穿透、雪崩和一致性？

答题关键词：

- 手机号和直播间查询使用短 TTL 空对象缓存，`UserServiceImpl#getUserById` 本身没有空值缓存。
- 批量用户缓存使用随机 TTL，主要缓解同时过期造成的雪崩。
- 用户更新采用更新 DB、删缓存、Kafka 加本地 DelayQueue 再删。
- 延迟双删只缩小不一致窗口，不保证强一致。

追问：热点 key 击穿怎么办？

回答思路：互斥重建、逻辑过期、热点不过期加主动刷新；还要考虑锁失败和旧值可接受时间。

### 问题 7：为什么用 `InheritableThreadLocal`，有什么问题？

答题关键词：

```text
请求内快速获取 userId
子线程创建时继承副本
线程池线程不会在每次提交时自动继承
工作线程复用造成泄漏/串用户
当前 postHandle 异常路径清理风险
```

生产改进：显式传参，或受控上下文包装；在 `afterCompletion/finally` 清理。

## 第三轮：Netty IM

### 问题 8：为什么使用 Netty 和 WebSocket？

答题关键词：

```text
双向长连接、服务端主动推送
NIO + Reactor
Boss 接收连接，Worker 处理 IO
Pipeline 和 Handler
避免每连接一阻塞线程
```

追问：EventLoop 中能直接执行慢 Dubbo 或数据库调用吗？

回答思路：不应长时间阻塞，否则同 EventLoop 上多个 Channel 都受影响；移交业务线程池并控制队列、超时和回写线程安全。

### 问题 9：IM 集群如何把消息发到正确机器？

闭卷调用链：

```text
本机 userId -> Channel
Redis userId -> IM Dubbo 地址
Router 批量查询并按地址分组
RpcContext 传目标 IP
自定义 Dubbo Cluster 精确选实例
目标实例本机 Map 找 Channel
```

追问：用户断线重连到新实例，旧离线事件晚到怎么办？

回答思路：绑定中保存 connectionId/version/loginTime；上线和离线用 Lua/CAS 条件更新，旧连接只能删除自己的版本。

### 问题 10：直播间群聊如何扇出？

答题关键词：

```text
Biz Handler -> Kafka
msg-provider
living-provider Redis Set/SSCAN
排除发送者
Router 按 IM 实例分组
本地 Channel 广播
```

追问：百万用户大房间如何优化？

回答思路：按 IM 实例维护房间订阅，服务端到 IM 实例级扇出，再本机广播；冷热分层、批量、背压、丢弃低价值事件、分级消息。

### 问题 11：ACK 解决了什么，为什么仍会重复？

回答思路：ACK提高服务端到客户端的可达性；ACK 丢失会触发重发，所以是至少一次语义，客户端用 msgId 去重。当前延迟调度在本地 DelayQueue，恢复还依赖 Kafka offset 和提交配置。

## 第四轮：Kafka、资金、红包和秒杀

### 问题 12：Kafka 怎样做到尽量不丢消息？

分三端回答：

- producer：`acks=all`、合理重试、幂等生产、检查异步结果。
- broker：多副本、合理 `min.insync.replicas`、监控 ISR。
- consumer：业务成功后提交 offset、失败重试/DLT、幂等处理。

加分点：消息可靠不等于业务可靠，业务落库与发消息还需要 Outbox/事务消息等方案。

### 问题 13：送礼当前如何幂等，哪里不够？

当前源码：消息 UUID + Redis `setIfAbsent` + 5 分钟 TTL。

不足：入口重试新 UUID、去重标记写得早、失败状态不可重试、TTL 后可重复、Redis 不是资金审计账本。

生产改进：稳定交易号、数据库唯一索引、处理状态机、扣款流水同键、对账。

### 问题 14：余额最终一致性如何实现和升级？

当前源码：Redis先扣，进程内线程池异步更新 MySQL 余额与流水。

风险：崩溃丢任务、队列拒绝、锁过期、重复消费。

升级：MySQL 条件更新余额 + 唯一流水 + Outbox 同事务，Kafka可靠发布，Redis作为缓存/预检查，定时对账。

### 问题 15：红包 `rightPop` 为什么不能保证一人一份？

回答思路：它只保证每个 List 元素被弹出一次，不记录 userId。使用 Lua 原子完成活动检查、用户 `HSETNX`、金额 pop 和领取记录；DB 用活动 ID + 用户 ID 唯一。

### 问题 16：Lua 原子扣库存后为什么仍可能不一致？

回答思路：Lua只覆盖 Redis 中一次检查和扣减；建单可能失败，Kafka 可能失败，支付和取消会竞争，MySQL同步也可能失败。需要库存预占记录、订单状态机、可靠超时任务和对账补偿。

### 问题 17：支付和超时回滚并发时怎么办？

回答思路：双方都用 `WHERE status = PREPARE_PAY` 做 CAS。支付更新成功才扣款/确认库存；取消更新成功才释放库存。失败方读取最终状态，不重复执行。

### 问题 18：为什么本地 DelayQueue 不可靠？

回答思路：只在 JVM 内存，重启丢任务；Kafka listener 可能已提交 offset；多实例和 rebalance 造成任务归属问题。使用可靠延迟消息或持久化过期时间扫描，执行仍要幂等。

## 源码评审加试

在 5 分钟内说出下列代码的触发条件和影响：

1. `RequestLimitInterceptor#preHandle` 第一行直接返回 `true`。

### 任务 2：10 分钟写四条链路

#### 鉴权

```text
Cookie -> Gateway -> Dubbo account -> Redis -> Header -> Interceptor -> Context
```

#### 群聊

```text
WebSocket -> Biz Handler -> Kafka -> msg-provider -> living Redis Set
-> Router -> 定向 Dubbo -> IM -> Channel
```

#### 送礼

```text
HTTP -> Caffeine -> Kafka -> Redis 去重 -> bank 扣款
-> living 在线用户 -> Router -> IM
```

#### 秒杀

```text
开播预热 -> Lua 扣 Redis 库存 -> 待支付订单
-> Kafka/DelayQueue -> 状态检查 -> 回滚 -> 定时同步 MySQL
```

### 任务 3：每条链路指出 3 个问题

问题必须按这个句式：

```text
当……发生时，当前……会导致……；生产上用……，幂等键/状态保存在……。
```

示例：

```text
当 send-gift 消费在写入 Redis 去重 key 后、扣款前异常时，
Kafka 重投会被短 TTL key 跳过，导致这次送礼没有完成；
生产上用交易号和数据库处理状态，失败保持可重试，成功才标记完成。
```

### 任务 4：Redis 五种角色

| 角色 | 项目状态 | 关键边界 |
| --- | --- | --- |
| 缓存 | 用户、直播间、礼物相关数据 | Cache Aside、一致性、穿透/击穿/雪崩 |
| 在线状态 | 心跳 ZSet、直播间用户 Set | TTL、乱序事件、弱一致遍历 |
| IM 路由 | 用户到 IM 实例地址 | 重连版本、实例下线、绑定续期 |
| 余额 | 高并发读写和预扣 | 不能代替可靠账本、需流水和对账 |
| 红包/库存 | List 分配、Lua 扣减 | 原子操作不等于完整业务事务 |

### 任务 5：五类故障处理

| 故障 | 可落地处理 |
| --- | --- |
| 消息重复 | 稳定业务 ID、唯一索引、幂等状态机、客户端 msgId 去重 |
| 消息丢失 | producer 确认、broker 副本、消费后提交、Outbox、重试和 DLT |
| 服务重启 | 外部持久化状态、可靠延迟任务、重放、幂等恢复 |
| 并发支付/取消 | 订单旧状态条件 CAS，只有状态迁移成功者执行副作用 |
| 缓存不一致 | Cache Aside、可靠失效事件、版本号/CDC、过期和对账 |
