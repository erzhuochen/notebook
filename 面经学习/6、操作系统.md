
#### 耗时操作
1. 进程/线程上下文切换
2. 阻塞和唤醒
3. 系统调用
4. 进程创建、线程创建
5. 锁竞争
主要关注发生频率高或者会引起上下文切换的操作，比如系统调用、线程阻塞和唤醒、锁竞争、线程/进程创建、IO 操作等。进入内核态本身不是绝对不能接受，因为 CPU 调度和系统调用都需要内核参与。真正影响性能的是频繁的用户态和内核态切换，以及线程阻塞、唤醒带来的上下文切换成本。所以像 synchronized 锁升级里会先自旋，就是因为短时间等待时，自旋可能比马上阻塞再唤醒更划算。
**不是所有进入内核态都要优化；要优化的是高频、额外、可避免的内核态切换和上下文切换**。
#### 用户态和内核态

内核态：权限 Ring 0。位于虚拟地址空间的高地址区，
       所有进程共享同一份内核映射，可执行特权指令。

用户态：权限 Ring 3。位于虚拟地址空间的低地址区，
       每个进程有独立的用户空间，进程切换需要切换页表和上下文。

read() 系统调用过程：
1. 用户态调用 read()，执行 syscall 指令触发 trap
2. CPU 切换到 Ring 0，进入内核态（涉及栈切换、可能污染 CPU 缓存/TLB）
3. 内核查 Page Cache：
   - 命中 → 直接拷贝到用户缓冲区
   - 未命中 → 发起磁盘 DMA 读取，当前进程睡眠等待
4. 数据到达后，从内核缓冲区拷贝到用户空间
5. 切换回 Ring 3 用户态，返回结果

上下文切换辨析：
- **系统调用**：只做模式切换（用户态→内核态），不切换进程，
  仍在当前进程上下文中执行，开销较小
- **异常**（如缺页）：同上，也在当前进程上下文中处理
- **硬件中断**：进入中断上下文，不属于任何进程，不能睡眠
- 进程切换：需要切换页表、寄存器、栈等完整上下文，开销最大

| **安全性/隔离性**（安全） | 差：一个线程崩溃可能导致整个进程崩溃                                                  | 好：一个进程崩溃不影响其他进程                      |

#### 进程上下文切换流程
- **触发中断/系统调用，陷入内核（Mode Switch）：** 进程 A 正在执行，由于时间片耗尽、发起 I/O 请求或硬件中断，CPU 的运行级别从 Ring 3（用户态）切换到 Ring 0（内核态）。
    
- **保存进程 A 的上下文（Save Context）：** CPU 将当前进程 A 的运行状态（包括 CPU 寄存器值、PC 程序计数器、SP 栈指针等）压入进程 A 的**内核栈**中，并更新 A 的 **PCB（Process Control Block，进程控制块）**。
    
- **调度器介入（Scheduling）：** 操作系统的调度算法（如 Linux 的 CFS 完全公平调度器）从就绪队列中选择下一个要执行的进程，假设为进程 B。
    
- **切换虚拟地址空间（Switch Address Space - 进程切换特有）：** CPU 将进程 B 的页表物理地址加载到页表基址寄存器（如 x86 的 CR3）。 _💡 面试高分提示：_ 这一步会导致之前的 TLB 缓存失效，进而导致后续内存访问经常发生 Cache Miss，这是进程切换代价高昂的根本原因。
    
- **恢复进程 B 的上下文（Restore Context）：** CPU 从进程 B 的 PCB/内核栈中，将之前保存的上下文数据**重新加载到 CPU 的物理寄存器中**（包括恢复进程 B 的 PC 值和 SP 值）。
    
- **返回用户态并继续执行（Return to User Mode）：** 执行特定的中断返回指令（如 `iret`），CPU 的运行级别由 Ring 0 恢复到 Ring 3。此时 CPU 的 PC 寄存器已经指向了进程 B 的下一条指令，进程 B 恢复执行。


#### 协程与进程
- 线程：操作系统分配CPU资源和调度的最小执行单位。
- 协程：运行在用户态的轻量级伪线程。它由程序代码控制的代码执行流程。

| **比较维度**    | **传统线程（Java 平台线程）**                       | **协程（Java 虚拟线程）**                   |
| ----------- | ----------------------------------------- | ----------------------------------- |
| **调度控制权**   | **操作系统内核** (Kernel Space)                 | **用户态运行时** (User Space，如 JVM)       |
| **调度方式**    | **抢占式** (时间片轮转，OS 强制剥夺)                   | 通常为**协作式** (遇到阻塞主动让出控制权)            |
| **上下文切换开销** | **极大**。需陷入内核态，切换寄存器、程序计数器，甚至刷新 TLB（页表缓存）。 | **极小**。纯用户态完成，仅需保存/恢复极少量的当前栈帧和局部变量。 |
| **内存占用**    | **大**。通常预留 1MB 左右固定栈空间。                   | **极小**。几 KB 起步，支持动态扩容。              |
| **并发量级**    | **几千级**（单机极易耗尽 CPU 调度和内存）                 | **百万级**（极其轻量，随便 new）                |

#### 进程通信方式
- 管道：接收方被动接收
- 消息队列：接收方主动从队列中取出需要的消息
- 共享内存：一块双方都能读写的内存，通信方式自由，想怎么读写都可以
- 信号：例如IO会产生信号告诉CPU去读取
- 信号量：本质就是一个用来计数的数，例如分配锁时设置信号量为3，线程使用一个锁，信号量减一，信号量为0时，请求锁的线程需自旋等待或睡眠等待信号（上面提到的那个信号）提醒。
- socket：一种逻辑概念，抽象出通信的接口，两个socket之间能建连

| 方式         | 原理                               | 特点                                         | 适用场景                   |
| ---------- | -------------------------------- | ------------------------------------------ | ---------------------- |
| **管道**     | 内核中的环形缓冲区，半双工，数据先进先出             | 简单；匿名管道仅限父子进程；数据读走即消失                      | 简单的父子进程通信，如 shell 管道   |
| **消息队列**   | 内核中的链表，按消息类型存取                   | 可按类型选择性接收；有格式；生命周期独立于进程                    | 需要结构化数据、解耦的通信          |
| **共享内存**   | 多个进程映射同一块物理内存                    | **最快**（零拷贝）；但必须自行解决同步问题                    | 大数据量、高频率通信             |
| **信号**     | 发给进程的异步通知（编号）。<br>区分：IO时发送的是硬件中断 | 只能传一个信号编号，不传数据；异步                          | 通知进程某事件发生（kill、Ctrl+C） |
| **信号量**    | 受保护的计数器 + P/V 操作                 | 本质是**同步机制**，不传数据                           | 控制并发数量、互斥访问            |
| **Socket** | 抽象的通信端点（IP+端口 或 文件路径）            | **唯一可跨机器**的 IPC；也可本机通信（Unix Domain Socket） | 网络通信、跨机器进程间通信          |

|IPC 方式|Java / 中间件映射|
|---|---|
|管道|`ProcessBuilder` 启动子进程时的输入输出流|

#### select / poll / epoll 底层对比

##### 1. `select` (机制落后，性能瓶颈严重)

- **存储结构**：Bitmap（位图，即 `fd_set`）。
    
- **运行机制**：将记录所有监控 fd 的位图从用户态拷贝到内核态；内核态通过 **$O(N)$ 轮询**遍历整个位图，找出发生事件的活跃 fd，再将修改后的位图拷贝回用户态。
    
- **三大缺陷**：
    
    1. **数量限制**：受限于位图大小，默认最大只能监控 1024 个 fd。
        
    2. **开销巨大**：每次调用都必须在用户态和内核态之间**全量拷贝**所有 fd。
        
    3. **状态不可重用**：内核会修改原位图来标记活跃事件，导致每次调用前必须在用户态重新初始化位图。
        

##### 2. `poll` (换汤不换药的伪升级)

- **存储结构**：`pollfd` 结构体数组（包含 fd、关注事件、发生事件）。
    
- **运行机制**：底层运转逻辑与 `select` 完全一致，依然是**全量拷贝 + $O(N)$ 轮询遍历**。
    
- **核心改进**：突破了 1024 的数量硬限制（仅受限于系统最大文件句柄数）；且分离了“关注事件”与“发生事件”，数组状态可重用，无需每次重新初始化。
    
- **缺陷**：当并发连接海量（如 10万）但活跃极少时，无意义的拷贝和遍历依然会导致 CPU 灾难。
    

##### 3. `epoll` (事件驱动，现代高性能网络基石)

- **存储结构**：**红黑树**（存储所有要监控的 fd） + **双向链表**（存储真正就绪的活跃 fd），这两者全部常驻在**内核空间**。
    
- **运行机制（彻底解耦）**：
    
    - **$O(\log N)$ 添加**：调用 `epoll_ctl` 将 fd 挂载到红黑树，**每个 fd 只发生一次拷贝**，消灭了全量拷贝开销。
        
    - **$O(1)$ 获取就绪**：基于**事件回调机制**，网卡收到数据后触发硬/软中断，底层回调函数直接把活跃的 fd 放入“就绪链表”中。
        
    - 调用 `epoll_wait` 时，只需检查“就绪链表”是否为空，并**只把活跃的少数 fd 拷贝回用户态**，彻底消灭了 $O(N)$ 的盲目遍历。
