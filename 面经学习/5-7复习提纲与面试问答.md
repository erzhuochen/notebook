# 5-7 复习提纲与面试问答

适用范围：计算机网络、操作系统、Java 并发。  
学习方式：先按体系主线复习，再用面试问答训练表达。

---

# 5. 计算机网络

## 学习目标

能从“一次浏览器请求到后端服务响应”出发，讲清 DNS、TCP、TLS、HTTP、认证状态和常见安全问题。

## 核心主线

```text
输入 URL
-> DNS 解析域名
-> 建立 TCP 连接
-> HTTPS 场景进行 TLS 握手
-> 浏览器发送 HTTP 请求
-> 服务端处理请求
-> 返回 HTTP 响应
-> 浏览器解析响应
```

## 必会知识点

### HTTP

- HTTP 是应用层协议，核心是请求和响应。
- HTTP/1.1 支持长连接，但同一连接上的请求仍容易受到队头阻塞影响。
- HTTP/2 引入二进制分帧、多路复用、头部压缩、服务端推送，提升并发传输能力。
- HTTP/3 基于 QUIC/UDP，把连接管理、可靠传输、加密握手下沉到 QUIC，减少 TCP 层队头阻塞。

### HTTPS / TLS

- HTTPS = HTTP + TLS。
- TLS 解决三个问题：身份认证、加密传输、完整性校验。
- 证书用于证明服务端身份，浏览器会校验证书链、域名、有效期和签名。
- 握手阶段通常使用非对称加密或密钥交换算法协商会话密钥，后续数据使用对称加密。

### TCP

- TCP 提供可靠、有序、面向连接的字节流传输。
- 三次握手用于确认双方收发能力，并同步初始序列号。
- 四次挥手用于双方各自关闭发送方向。
- TCP 通过序列号、确认号、重传、滑动窗口、拥塞控制保证可靠性和性能。

### DNS

- DNS 用于把域名解析成 IP。
- 常见过程：浏览器缓存 -> 系统缓存 -> 本地 DNS -> 根域名服务器 -> 顶级域名服务器 -> 权威域名服务器。
- DNS 解析可能受到缓存、TTL、CDN 调度影响。

### Cookie / Session / Token

- Cookie 存在客户端，常用于保存会话标识或偏好。
- Session 数据存在服务端，客户端通常只保存 SessionId。
- Token/JWT 通常由服务端签发，客户端携带，服务端校验签名和有效期。
- 后端校招回答时要说清楚：存哪里、服务端是否有状态、适合什么场景、安全风险是什么。

### XSS / CSRF

- XSS 是恶意脚本被注入并在用户浏览器执行。
- CSRF 是攻击者利用用户已登录状态，诱导浏览器向目标站点发起请求。
- XSS 重点防输入和输出，CSRF 重点验证请求来源和 Token。

## 易错点

- HTTPS 不是只靠非对称加密传输全部数据，真正业务数据通常使用对称加密。
- HTTP/2 多路复用解决的是 HTTP 层队头阻塞，但 TCP 丢包仍会影响连接上的所有流。
- Token 放在客户端不等于绝对安全，仍然要考虑过期、刷新、泄露和撤销。
- CSRF 不一定需要攻击者读取响应，只要能诱导浏览器发出带 Cookie 的请求就可能成立。

## 面试问答附录

### Q1：从输入 URL 到页面返回，发生了什么？

标准回答：

> 浏览器先解析 URL，检查缓存，然后通过 DNS 把域名解析成 IP。拿到 IP 后和服务端建立 TCP 连接，如果是 HTTPS，还要进行 TLS 握手，校验证书并协商会话密钥。之后浏览器发送 HTTP 请求，服务端处理后返回 HTTP 响应，浏览器再解析响应内容并渲染页面。

追问：

- DNS 解析流程是什么？
- HTTPS 握手解决了什么问题？
- HTTP/2 和 HTTP/1.1 有什么区别？

项目关联说法：

> 在后端项目里，我更关注请求进入服务后的链路，比如网关鉴权、Controller 参数校验、业务处理、数据库/Redis 访问，以及响应耗时。网络层面如果接口慢，我会先区分是 DNS/TCP/TLS 慢，还是服务端业务处理慢。

### Q2：HTTP 和 HTTPS 有什么区别？

标准回答：

> HTTP 是明文传输，HTTPS 在 HTTP 之上加入 TLS，能提供加密传输、身份认证和完整性校验。HTTPS 会多一次 TLS 握手，但现在通过会话复用、HTTP/2、HTTP/3 等方式已经能把额外开销控制得比较低。

回答陷阱：

- 不要说 HTTPS 绝对安全。
- 不要说 HTTPS 全程只用非对称加密。

### Q3：Cookie、Session、Token 有什么区别？

标准回答：

> Cookie 是客户端存储机制，可以保存 SessionId 或 Token。Session 是服务端保存用户状态，客户端只带 SessionId。Token 通常是服务端签发、客户端保存、请求时携带，服务端通过签名和有效期校验。Session 更适合传统单体，Token 更适合前后端分离和分布式系统。

追问：

- JWT 如何失效？
- Token 放 Cookie 还是 Header？
- Session 在分布式下怎么做？

### Q4：XSS 和 CSRF 的区别？

标准回答：

> XSS 是攻击者把恶意脚本注入页面，让脚本在用户浏览器执行；CSRF 是攻击者利用用户已登录状态，诱导浏览器自动带 Cookie 去请求目标网站。XSS 防御重点是输入过滤、输出转义、CSP、HttpOnly；CSRF 防御重点是 CSRF Token、SameSite Cookie、Origin/Referer 校验。

### Q5：TCP 为什么需要三次握手？

标准回答：

> 三次握手主要是为了确认客户端和服务端的发送、接收能力都正常，并同步双方初始序列号。两次握手只能让服务端确认客户端能发、服务端能收，但客户端还不能确认服务端能发、客户端能收，也容易受到历史连接请求影响。

# 6. 操作系统

## 学习目标

能从 Java 后端运行时视角理解进程线程、用户态/内核态、上下文切换、进程通信和 IO 多路复用。

## 核心主线

```text
一个后端服务 = 一个 JVM 进程
一个请求 = 通常由某个线程处理
线程执行过程中可能访问内存、加锁、读写网络/磁盘
涉及系统调用时会进入内核态
高并发下要减少阻塞、上下文切换和无效轮询
```

## 必会知识点

### 进程和线程

- 进程是资源分配的基本单位，拥有独立地址空间。
- 线程是 CPU 调度的基本单位，同一进程内线程共享堆、方法区、文件描述符等资源。
- Java 后端中，一个 Spring Boot 应用通常是一个 JVM 进程，请求由线程池中的线程处理。

### 用户态和内核态

- 用户态权限低，应用程序大部分逻辑运行在用户态。
- 内核态权限高，可以访问硬件和系统资源。
- 系统调用会从用户态切换到内核态，例如 read、write、socket、accept。

### 上下文切换

- 线程/进程切换时，CPU 需要保存当前执行现场，再恢复另一个执行现场。
- 进程切换比线程切换更重，因为涉及地址空间、页表、TLB 等。
- 高并发下频繁阻塞、锁竞争、线程数过多都会增加上下文切换成本。

### 进程通信

- 常见 IPC：管道、消息队列、共享内存、信号、信号量、Socket。
- 共享内存速度快，但需要额外同步机制。
- Socket 是最常见的跨机器通信基础。

### IO 多路复用

- select/poll/epoll 都是让一个线程管理多个连接的机制。
- select 有 fd 数量限制，每次都要复制和遍历。
- poll 取消固定数量限制，但仍然需要遍历。
- epoll 通过事件驱动，只关注就绪连接，更适合大量连接、少量活跃的场景。

## 易错点

- 进入内核态不一定等于进程切换。
- 线程越多不一定性能越好，线程过多会带来调度和上下文切换成本。
- epoll 不是所有场景都一定最快，它适合大量连接且活跃连接较少的场景。

## 面试问答附录

### Q1：进程和线程有什么区别？

标准回答：

> 进程是资源分配的基本单位，有独立地址空间；线程是 CPU 调度的基本单位，同一进程内的线程共享进程资源，但每个线程有自己的栈、程序计数器和寄存器上下文。线程切换通常比进程切换轻量，但线程共享内存，所以需要考虑线程安全。

项目关联说法：

> Java 后端服务启动后就是一个 JVM 进程，Tomcat 或业务线程池里的线程负责处理请求，所以线程池参数、锁竞争、阻塞 IO 都会影响服务吞吐。

### Q2：用户态和内核态有什么区别？

标准回答：

> 用户态是普通应用运行的状态，权限较低；内核态是操作系统内核运行的状态，权限高，可以访问硬件和系统资源。应用如果要读写文件、网络通信、创建线程等，需要通过系统调用进入内核态。

追问：

- 系统调用和上下文切换是不是一回事？
- 为什么频繁系统调用会影响性能？

### Q3：什么是上下文切换？为什么它有成本？

标准回答：

> 上下文切换是 CPU 从一个线程或进程切换到另一个线程或进程执行时，保存当前运行状态并恢复另一个运行状态的过程。它需要保存和恢复寄存器、程序计数器、栈等信息，进程切换还可能涉及页表和 TLB，所以频繁上下文切换会降低性能。

### Q4：select、poll、epoll 有什么区别？

标准回答：

> select 使用位图，有 fd 数量限制，每次调用都要从用户态复制到内核态并遍历所有 fd。poll 使用数组，解决了数量限制，但仍然要遍历。epoll 把关注的 fd 保存在内核中，通过事件回调维护就绪队列，调用 epoll_wait 时只返回就绪 fd，因此更适合高并发网络服务器。

### Q5：为什么 Java 后端要理解操作系统？

标准回答：

> 因为 Java 后端的性能问题经常和操作系统有关，比如线程阻塞、上下文切换、网络 IO、文件 IO、内存分页、CPU 调度等。理解这些概念后，排查接口慢、CPU 高、线程池打满、连接数过多时会更有方向。

# 7. Java 并发

## 学习目标

能围绕“多线程共享数据如何保证正确性和性能”讲清 JMM、锁、CAS、AQS、线程池、ThreadLocal 和并发容器。

## 核心主线

```text
多线程共享数据
-> 出现原子性、可见性、有序性问题
-> JMM 定义内存可见性规则
-> volatile / synchronized / Lock 解决不同问题
-> CAS 和 AQS 支撑 JUC
-> 线程池管理线程资源
-> ThreadLocal 处理线程隔离变量
-> 并发容器解决集合线程安全问题
```

## 必会知识点

### JMM 与 volatile

- JMM 解决多线程下共享变量的可见性和有序性问题。
- volatile 保证可见性，禁止指令重排序，但不保证复合操作的原子性。
- happens-before 是判断一个操作结果是否对另一个操作可见的规则。

### synchronized

- synchronized 可以修饰实例方法、静态方法、代码块。
- 实例方法锁当前对象，静态方法锁 Class 对象，代码块锁括号中的对象。
- 它保证原子性、可见性和有序性。
- 锁升级过程通常包括无锁、偏向锁、轻量级锁、重量级锁。

### CAS 与原子类

- CAS 包含内存值 V、期望值 A、新值 B。
- 当 V == A 时，把 V 更新为 B，否则失败重试。
- 优点是无锁，缺点是 ABA、自旋开销、只能保证单变量原子性。

### AQS

- AQS 是很多 JUC 锁和同步器的基础。
- 核心是 state 状态变量和 FIFO 等待队列。
- ReentrantLock、Semaphore、CountDownLatch 等都基于 AQS 思想实现。

### 线程池

- 线程池复用线程，减少频繁创建销毁线程的成本，并统一管理并发量。
- 核心参数：corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、handler。
- 执行流程：核心线程 -> 阻塞队列 -> 非核心线程 -> 拒绝策略。
- 不推荐 Executors，因为可能创建无界队列或过多线程，导致 OOM。

### ThreadLocal

- ThreadLocal 为每个线程保存独立变量副本。
- 常用于用户上下文、链路追踪、数据库连接上下文等。
- 在线程池场景下必须 remove，避免脏数据和内存泄漏。

### 并发容器

- ConcurrentHashMap 使用 CAS + synchronized 等机制保证线程安全。
- CopyOnWriteArrayList 适合读多写少。
- BlockingQueue 常用于生产者消费者和线程池任务队列。

## 易错点

- volatile 不能保证 i++ 的原子性。
- synchronized 锁的是对象，不是代码本身。
- ThreadLocal 不是为了解决共享变量竞争，而是避免共享。
- 线程池最大线程数不是越大越好，要结合 CPU 密集/IO 密集任务设置。
- submit 吃掉异常时要从 Future 中获取，否则可能不明显。

## 面试问答附录

### Q1：volatile 有什么作用？

标准回答：

> volatile 主要有两个作用：保证变量修改对其他线程可见，禁止指令重排序。它适合状态标记、单例双重检查锁等场景。但 volatile 不保证复合操作的原子性，比如 i++ 包含读取、加一、写回多个步骤，所以不能只靠 volatile 保证线程安全。

追问：

- volatile 为什么不能保证 i++ 安全？
- 双重检查锁为什么要加 volatile？

### Q2：synchronized 锁的是什么？

标准回答：

> synchronized 锁的是对象。修饰普通实例方法时锁当前实例对象；修饰静态方法时锁 Class 对象；修饰代码块时锁括号里指定的对象。它通过 monitor 机制实现互斥，并在进入和退出同步块时保证可见性。

回答陷阱：

- 不要说 synchronized 锁的是方法或代码块，准确说锁的是对象。

### Q3：CAS 是什么？有什么问题？

标准回答：

> CAS 是 Compare And Swap，比较并交换。它会比较内存中的当前值是否等于期望值，如果相等就更新为新值，否则失败重试。CAS 可以实现无锁原子更新，但存在 ABA 问题、自旋开销大、只能保证单变量原子性等问题。

### Q4：AQS 是什么？

标准回答：

> AQS 是 AbstractQueuedSynchronizer，是 JUC 中很多锁和同步器的基础框架。它用一个 state 表示同步状态，用一个 FIFO 队列管理等待线程。获取资源失败的线程会进入队列等待，释放资源时再唤醒后续线程。ReentrantLock、Semaphore、CountDownLatch 都和 AQS 有关。

### Q5：线程池执行任务的流程是什么？

标准回答：

> 提交任务后，如果运行线程数小于 corePoolSize，就创建核心线程执行；否则尝试放入阻塞队列；如果队列满了，并且线程数小于 maximumPoolSize，就创建非核心线程执行；如果还不能处理，就执行拒绝策略。

追问：

- 为什么不推荐 Executors？
- 拒绝策略有哪些？
- CPU 密集型和 IO 密集型线程数怎么设置？

### Q6：ThreadLocal 为什么可能内存泄漏？

标准回答：

> 每个线程内部有 ThreadLocalMap，key 是 ThreadLocal 的弱引用，value 是实际对象。如果 ThreadLocal 外部强引用没了，key 可能被回收，但 value 还被线程持有。在线程池中线程长期存活，value 可能一直无法释放，所以使用完 ThreadLocal 后建议调用 remove。

### Q7：ConcurrentHashMap 如何保证线程安全？

标准回答：

> JDK 1.8 的 ConcurrentHashMap 主要使用 CAS 和 synchronized。插入空桶时通常用 CAS，发生哈希冲突时锁住桶头节点进行链表或红黑树操作。它锁粒度比 Hashtable 小，能在保证线程安全的同时提高并发性能。

### Q8：CompletableFuture 解决了什么问题？

标准回答：

> Future 可以表示异步任务结果，但获取结果通常要阻塞，多个异步任务组合也不方便。CompletableFuture 支持异步编排、任务串联、并行汇总和异常处理，更适合多个远程调用或 IO 任务并发执行后汇总结果的场景。
