# 短信条数拦截配置：测试用例（只用网页操作）

全部用网页操作：
- 在**管理台**改配置。
- 在**用户端**（官网 / H5 的登录或注册页）点「获取验证码」，触发 OTP 短信。

判断是否通过看三处：**手机有没有收到验证码**、**Redis 计数**、**数据库**。notification 日志能看到的话可以作为补充，看不到也不影响判断。

## 0. 准备

### 0.1 注意事项
- **用户端发验证码不会显示"被拦截"。** 拦截发生在 MQ 下游，用户端照样提示发送成功，所以判断是否被拦截只能看：手机没收到短信，且 Redis 计数没有增加。
- **测试会影响同一区号下的其他测试人员。** 测试用的是你手机的真实区号（下面按 `+86` 举例），测试期间同区号的其他人也会被拦。**测试结束后务必删除 `+86` 这条配置**，见第 4 节。
- **不要用华为渠道账号测试。** 华为应用市场渠道（channel=100351）的 `+86` 用户走的是另一个队列，不经过这次的拦截逻辑。
- **两次获取验证码之间要等倒计时结束**（一般 60 秒）。
- **每次修改配置前先读一次计数。** 同区号可能有其他人在发验证码，所以每步都先读当前计数，再按读到的值来设上限，不要用固定数字。
- **告警短信的接收人。** 拦截时会给 nacos 里 `sms.optLimitNotify` 配置的号码发告警短信。如果能改，建议先改成你自己的手机号，这样也能作为判断依据。

### 0.2 怎么读计数（Redis）
计数 key 的日期和小时取的是 notification 服务器的本地时间，用通配符查最稳：
```bash
redis-cli --scan --pattern 'OTP_LIMIT_2*+86'
# 会列出两个 key：
#   OTP_LIMIT_20261016+86     ← 天计数，下文记作 D（8 位日期）
#   OTP_LIMIT_2026101614+86   ← 小时计数，下文记作 H（10 位日期+小时）
redis-cli GET  'OTP_LIMIT_20261016+86'
redis-cli TTL  'OTP_LIMIT_20261016+86'
```
- 如果查出多个 8 位日期的 key，取日期最大的那个。
- 如果测试过程中跨了整点，H 会换成新 key，换了就重新查一次。
- Redis 是集群的话加 `-c`，也可以用图形化客户端搜索。

缓存配置：
```bash
redis-cli HGETALL WT:SMS:OTP_LIMIT:DAY
redis-cli HGETALL WT:SMS:OTP_LIMIT:HOUR
```

### 0.3 数据库（panda_db）
```sql
SELECT * FROM sms_limit_config;   -- 要有 DEFAULT 行；没有的话先在管理台新增
```

## 1. 管理台配置功能

入口：消息中心 → 短信条数拦截配置。

| 编号 | 操作 | 判断通过 |
| --- | --- | --- |
| M1 | 打开页面 | 菜单可见，列表里有 DEFAULT 行。DEFAULT 行**没有删除按钮** |
| M2 | 点工具箱的「刷新缓存」并确认 | 提示"刷新成功！"。`HGETALL` 两个 hash 都有 `DEFAULT`，值和库里一致，而且是纯数字（不带引号或 `@class`）。`TTL WT:SMS:OTP_LIMIT:DAY` 返回 `-1` |
| M3 | 修改 DEFAULT 行 | 区号只读；状态里的"停用"选项灰掉、不可选 |
| M4 | 修改 DEFAULT 行，把"每小时上限"清空后提交 | 提示"DEFAULT 配置必须填写每天和每小时上限"，库里没变 |
| M5 | 新增，上限填 `-1` 或 `1.5` | 提示"上限只能填写非负整数" |
| M6 | 新增，区号填 `abc` | 提示"区号格式不正确，例如：+86"，库里没有新记录 |
| M7 | 新增，区号填 `86`（不带 +），每天上限 `100000`，每小时上限**留空** | 保存成功。列表里区号显示 `+86`，每小时上限显示灰字"继承DEFAULT"。库里 `area_code='+86'`，`hour_limit IS NULL`，`update_by` 是你的管理台账号名。`HGET WT:SMS:OTP_LIMIT:DAY +86` 返回 `100000`，`HEXISTS WT:SMS:OTP_LIMIT:HOUR +86` 返回 `0` |
| M8 | 再新增一次 `+86` | 提示"区号 +86 已存在" |
| M9 | 搜索区号 `86` | 查到 `+86` 这一行 |
| M10 | 搜索状态"停用" | 不显示启用中的记录 |

## 2. 发送拦截

前提：M7 已完成，库里有 `+86`。每步都是"先读 D/H → 在管理台改 `+86` → 在用户端获取一次验证码 → 再读 D/H"。

| 编号 | 管理台设置（d、h 为本步开始时读到的 D、H 值） | 用户端操作 | 判断通过 |
| --- | --- | --- | --- |
| S1 正常发送 | 每天 `100000`，每小时留空 | 获取验证码 | **收到短信**。D 和 H 各加 1，D 的 TTL 约 86400，H 的 TTL 约 3600 |
| S2 刚好放行最后一条 | 每天 `d+1`，每小时留空 | 获取验证码 | **收到短信**，D 变成 `d+1` |
| S3 日拦截 | 不改，保持 S2 的设置（此时 D 已经等于上限） | 倒计时结束后再获取一次 | **收不到短信**。D 和 H 都**不变**。出现 key `OTP_LIMIT_NOTIFY_DATE{8位日期}+86`，值是当天日期，TTL 约 90000。告警号码收到"⚠️警告：**单日**验证码超限……"。有日志的话能看到 `维度:每天` |
| S4 告警只发一次 | 不改 | 再获取一次 | 仍然收不到短信。**不会**再收到告警短信。上面那个告警 key 的 TTL 继续往下走，没有被重置 |
| S5 小时拦截并回退日计数 | 每天 `100000`，每小时 `h`（等于当前小时计数） | 获取验证码 | **收不到短信**。D **不变**：先加 1，又被回退。H 不变。出现 `OTP_LIMIT_NOTIFY_DATE{10位日期小时}+86`。告警短信写的是"**单小时**验证码超限" |
| S6 禁发 | 每天 `0`，每小时留空 | 获取验证码 | **收不到短信**，D 不变。列表里每天上限显示红字"0（禁发）" |
| S7 停用后回落 DEFAULT | 保持 S6 的上限，状态改成「停用」 | 获取验证码 | `HEXISTS WT:SMS:OTP_LIMIT:DAY +86` 返回 `0`。**收到短信**（改用 DEFAULT 的上限），D 加 1 |
| S8 修改即时生效 | 状态改回「启用」，每天 `0` | 获取验证码 | 改完立刻就**收不到**了，不用重启，也不用手动刷新 |
| S9 删除后回落 DEFAULT | 在列表里删除 `+86`，弹出确认框后确认 | 获取验证码 | 库里和两个 hash 里都没有 `+86`。**收到短信** |

## 3. 兜底与兼容（需要在 Redis 里手动执行命令）

| 编号 | 操作 | 判断通过 |
| --- | --- | --- |
| F1 缓存丢失后自动回填 | `redis-cli DEL WT:SMS:OTP_LIMIT:DAY WT:SMS:OTP_LIMIT:HOUR`，然后在用户端获取验证码 | **收到短信**。两个 hash **自动重新出现**，内容和库一致，没有人点过刷新 |
| F2 兼容旧计数 key | `redis-cli PERSIST '<D 的 key>'` 去掉 TTL（`TTL` 返回 `-1`），然后获取验证码 | D 在原值基础上加 1，TTL 恢复为约 86400。说明新逻辑能接着旧逻辑写下的值继续计数 |
| F3（可选）库里也没有 DEFAULT | 距 F1 **超过 60 秒**后执行：`UPDATE sms_limit_config SET status=0 WHERE area_code='DEFAULT';`，再 `DEL` 两个 hash，然后获取验证码 | **收到短信**（用代码里的默认上限 每天 500 / 每小时 200）。两个 hash **不会**被重建。有日志的话能看到 ERROR"缺少 DEFAULT" |
| F3 恢复 | `UPDATE sms_limit_config SET status=1 WHERE area_code='DEFAULT';`，然后在管理台点「刷新缓存」 | 两个 hash 恢复，都有 DEFAULT |

F3 要和 F1 间隔 60 秒以上：notification 会把回源查库的结果在本地保留 60 秒，间隔太短会直接用上次的结果。

| 编号 | 操作 | 判断通过 |
| --- | --- | --- |
| F4 回填不覆盖已有缓存 | 先 `DEL` 两个 hash，再执行 `redis-cli HSET WT:SMS:OTP_LIMIT:DAY DEFAULT 1` 和 `redis-cli HSET WT:SMS:OTP_LIMIT:HOUR DEFAULT 1`，造一份"只有 DEFAULT=1"的缓存，然后获取验证码 | notification 认为缓存存在，不回源，`HGETALL` 仍然只有 `DEFAULT=1`。这时上限是 1，当天已经发过的话这次会被拦截，属于预期。测完点「刷新缓存」恢复 |

## 4. 测试结束后必须清理

1. 在管理台删除 `+86` 和其他测试时新增的区号，只留下 DEFAULT 和正式配置。
2. 确认 DEFAULT 是启用状态，数值和测试前一致。
3. 点一次「刷新缓存」，执行 `HGETALL` 确认两个 hash 正常。
