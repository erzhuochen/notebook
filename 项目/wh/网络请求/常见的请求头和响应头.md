# 常见的请求头和响应头

## 基本认识

- 请求头由客户端发给服务器，用来描述请求、客户端能力和访问条件；响应头由服务器返回，用来描述响应内容和处理规则。
- 头名称不区分大小写，如 `Content-Type` 与 `content-type` 等价；头的值是否区分大小写取决于具体字段。HTTP/2、HTTP/3 的字段名使用小写。
- 有些头既能用于请求，也能用于响应，如 `Content-Type`、`Content-Length`、`Cache-Control`，需要结合方向理解。HTTP 方法、URL 和状态码本身不属于普通头字段。
- 浏览器会自动管理一部分请求头，不能把抓包中看到的头都原样写进 `fetch` 的 `headers`。例如 `Cookie`、`Host`、`Content-Length`、`Origin`、`Accept-Encoding` 不能由网页 JavaScript 任意设置。

基础语义可查阅 [RFC 9110：HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html)。

## 跨域相关

这里的“跨域”指跨源：协议、主机、端口中任意一项不同就不同源。`https://app.example.com` 与 `https://api.example.com` 也不同源。

以下预检说明针对浏览器跨源 `fetch`／XHR 的 CORS 流程；同源请求不会仅因为使用 JSON 或 `Authorization` 就触发 CORS 预检。

### 浏览器发送的请求头

| 请求头 | 作用 | 示例／出现时机 |
| --- | --- | --- |
| `Origin` | 标明发起请求的来源，通常包含协议、主机和非默认端口，不包含路径 | `https://app.example.com`；某些不透明来源会序列化为 `null` |
| `Access-Control-Request-Method` | 询问正式请求能否使用某个 HTTP 方法 | `POST`；仅 CORS 预检请求 |
| `Access-Control-Request-Headers` | 列出正式请求中需要服务器明确许可的请求头名称，不包含这些头的值 | `authorization, content-type, token`；仅 CORS 预检请求，并非列出全部请求头 |
| `Content-Type` | 声明请求体的媒体类型；跨源 CORS 请求使用 `application/json` 时需要预检 | `application/json`；预检缓存有效时可以省去新的预检 |
| `Authorization` | 携带标准 HTTP 认证信息；由代码设置该头的跨源 CORS 请求需要预检 | `Bearer <token>`；正式请求，服务器仍需验证 token |
| `token` | 业务自定义请求头，没有统一标准；用于跨源 CORS 请求时需要预检 | `<token>`；认证信息通常可使用标准的 `Authorization` |
| `Cookie` | 浏览器按目标 URL、凭据模式和 Cookie 规则自动携带会话等数据 | `sessionId=abc123`；携带 Cookie 本身不会触发预检 |

### 服务器返回的响应头

| 响应头 | 作用 | 示例／出现时机 |
| --- | --- | --- |
| `Access-Control-Allow-Origin` | 指定允许读取响应的来源；一次只能返回一个来源或 `*`，不能写逗号分隔的来源列表 | `https://app.example.com`；预检响应和正式响应都需要按场景返回 |
| `Access-Control-Allow-Methods` | 告诉浏览器正式请求允许使用哪些方法 | `GET, POST, PUT, DELETE`；用于预检响应 |
| `Access-Control-Allow-Headers` | 告诉浏览器正式请求允许携带哪些需要许可的请求头 | `Content-Type, Authorization, token`；用于预检响应 |
| `Access-Control-Allow-Credentials` | 允许凭据模式为 `include` 的跨源响应向网页开放 | `true`；只有小写 `true` 有效，不允许时省略该头 |
| `Access-Control-Expose-Headers` | 允许网页 JavaScript 读取默认范围之外的响应头 | `X-Request-Id, Content-Disposition`；用于正式响应 |
| `Access-Control-Max-Age` | 指定预检许可的缓存时间，单位为秒；这是独立于普通 HTTP 缓存的预检缓存 | `1800`；用于预检响应，实际受浏览器上限限制 |
| `Vary` | 告诉缓存按指定请求头区分响应；按来源动态返回 CORS 结果时应包含 `Origin` | `Origin`；已有其他值时追加，如 `Accept-Encoding, Origin` |

上述字段及处理流程见 [MDN：CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS) 和 [Fetch 标准：CORS 协议](https://fetch.spec.whatwg.org/#http-cors-protocol)。

### 容易混淆的规则

1. **不是所有跨源请求都需要预检。** 常见免预检情形是使用 `GET`、`HEAD` 或 `POST`，且代码设置的请求头及其值满足 CORS 安全列表要求。安全列表包括 `Accept`、`Accept-Language`、`Content-Language`、符合限制的 `Content-Type` 和 `Range`；其中 `Range` 须为符合要求的单一字节范围，如 `bytes=0-1023`，仅后缀范围 `bytes=-500` 不属于安全列表。字段值还有长度、字符等限制。流式请求体、XHR 上传事件监听等也可能影响预检。
2. **`Content-Type` 的安全列表只允许三种基本媒体类型：** `application/x-www-form-urlencoded`、`multipart/form-data`、`text/plain`。不能仅根据使用了 `POST` 就认定无需预检。
3. **Cookie 与预检是两件事。** 跨源 `fetch` 携带 Cookie 通常要设置 `credentials: 'include'`，XHR 则设置 `withCredentials = true`；服务端还需要明确的允许来源和 `Access-Control-Allow-Credentials: true`。按规范，预检请求不携带 Cookie 等凭据，服务端不应要求预检先通过会话认证。
4. **凭据模式为 `include` 时，`Access-Control-Allow-Origin` 不能是 `*`，即使这次实际上没有 Cookie。** `Access-Control-Allow-Headers`、`Access-Control-Allow-Methods`、`Access-Control-Expose-Headers` 的 `*` 在该模式下也不作为通配符；实际配置应明确列出所需项。另外，`Authorization` 在 `Access-Control-Allow-Headers` 中必须显式列出，不能靠 `*` 放行。
5. **允许携带 Cookie 不代表 Cookie 一定会发送。** 仍要满足域、路径、`Secure`、`SameSite` 以及浏览器第三方 Cookie 策略。跨源不等于跨站；跨站 `fetch`／XHR 携带 Cookie 通常还需要 Cookie 设置 `SameSite=None; Secure`。
6. **允许发送请求头与允许读取响应头不同。** 前者看 `Access-Control-Allow-Headers`，后者看 `Access-Control-Expose-Headers`。CORS 校验通过后，默认可读的响应头是 `Cache-Control`、`Content-Language`、`Content-Length`、`Content-Type`、`Expires`、`Last-Modified`、`Pragma`；`Set-Cookie` 即使被写入暴露列表也不能通过浏览器 `fetch`／XHR 的响应头 API 读取。
7. **预检通过后，正式响应仍要满足 CORS 校验。** 不能只给 `OPTIONS` 响应添加 CORS 头。动态返回允许来源时，应先检查来源白名单；`Vary: Origin` 只处理缓存区分，不负责判断来源是否可信。
8. **CORS 不代替登录认证、权限校验或 CSRF 防护。** 无需预检的请求可能已到达服务器并产生副作用，只是浏览器不允许 JavaScript 读取响应。`mode: 'no-cors'` 也不能让代码读取被限制的响应。

具体安全列表与通配符规则见 [Fetch 标准：头字段](https://fetch.spec.whatwg.org/#headers) 和 [CORS 与凭据](https://fetch.spec.whatwg.org/#cors-protocol-and-credentials)。

## 其他常见请求头

### 目标、来源与内容协商

| 请求头 | 作用 | 示例／注意事项 |
| --- | --- | --- |
| `Host` | 标明目标主机和可选端口，供服务器进行虚拟主机路由 | `api.example.com:8080`；HTTP/1.1 必需，HTTP/2、HTTP/3 通常使用 `:authority` 伪头表达 |
| `User-Agent` | 描述客户端软件及部分环境信息 | `Mozilla/5.0 ...`；可伪造，不能作为可信身份依据 |
| `Accept` | 表示客户端可接受的响应媒体类型 | `application/json`；`q` 表示相对偏好，例如 `text/html, application/json;q=0.9` |
| `Accept-Language` | 表示客户端偏好的响应语言 | `zh-CN, zh;q=0.9, en;q=0.8` |
| `Accept-Encoding` | 表示客户端支持的内容编码，常用于压缩协商 | `gzip, deflate, br`；通常由浏览器设置 |
| `Referer` | 表示请求的来源页面地址；发送多少信息由 Referrer Policy 等规则决定 | `https://app.example.com/list`；可能只有源，也可能不发送；字段名历史拼写就是 `Referer` |
| `Sec-Fetch-Site` | 标明发起方与目标的站点关系，供服务器判断请求上下文 | `same-origin`、`same-site`、`cross-site`、`none`；由浏览器设置 |
| `Sec-Fetch-Mode` | 标明请求模式 | `navigate`、`cors`、`no-cors`、`same-origin` |
| `Sec-Fetch-Dest` | 标明请求资源的用途 | `document`、`image`、`script`、`empty`；`fetch` 常见为 `empty` |

`Origin` 只表达来源，不带页面路径；`Referer` 可能包含路径。客户端偏好与实际返回结果也要区分：`Accept` 表示“希望收到什么”，响应的 `Content-Type` 才表示“实际返回什么”。这些字段可在 [MDN：HTTP 头参考](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers) 中按名称查阅。

### 请求体与认证

| 请求头 | 作用 | 示例／注意事项 |
| --- | --- | --- |
| `Content-Type` | 声明当前请求体的媒体类型 | `application/json`、`application/x-www-form-urlencoded`、`multipart/form-data; boundary=...` |
| `Content-Length` | 声明消息内容的字节数，不是字符数 | `128`；由浏览器或 HTTP 客户端计算；不一定每个请求都有 |
| `Content-Encoding` | 声明请求内容已经采用的编码；与请求体的媒体类型不同 | `gzip`；服务端必须支持相应解码 |
| `Authorization` | 向服务器提交认证信息 | `Bearer <token>`、`Basic <base64凭据>`；Basic 编码不等于加密，应通过 HTTPS 传输 |
| `Cookie` | 携带符合发送规则的 Cookie 键值对 | `sessionId=abc123; theme=dark`；这里不包含 `HttpOnly`、`SameSite` 等设置属性 |

用 `FormData` 上传文件时，通常直接把它作为请求体，让浏览器生成 `Content-Type` 和配套的 `boundary`；不要只手动填写 `multipart/form-data`。可参考 [MDN：CORS 中的表单请求示例](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS#simple_requests)。

### 缓存校验与范围请求

| 请求头 | 作用 | 示例／注意事项 |
| --- | --- | --- |
| `Cache-Control` | 表达客户端对本次请求的缓存要求 | `no-cache`：复用缓存前需向服务器验证；请求指令与响应指令的适用范围不同 |
| `If-None-Match` | 携带已有资源的 ETag，用于判断资源是否变化 | `"v1"`；对 `GET`／`HEAD`，匹配时通常返回 `304 Not Modified` |
| `If-Modified-Since` | 携带已有资源的修改时间，用于条件请求 | `Wed, 21 Oct 2026 02:00:00 GMT`；同时有 `If-None-Match` 时，后者优先 |
| `If-Match` | 只有当前资源满足指定 ETag 条件才执行操作，常用于避免并发覆盖 | `"v1"`；更新条件不满足时通常返回 `412 Precondition Failed`，使用强比较 |
| `Range` | 请求资源的部分字节，常用于视频播放和断点下载 | `bytes=0-1023`；含首尾，共 1024 字节；服务器可能忽略并返回完整内容 |
| `If-Range` | 配合 `Range`，仅在资源仍匹配校验标识时请求部分内容，否则请求完整内容 | `"v1"`；使用 ETag 时应使用强 ETag |

条件请求可参考 [MDN：ETag](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/ETag)；范围请求语义见 [RFC 9110：Range](https://www.rfc-editor.org/rfc/rfc9110.html#section-14.2)。

## 其他常见响应头

### 响应内容、下载与处理结果

| 响应头 | 作用 | 示例／注意事项 |
| --- | --- | --- |
| `Content-Type` | 声明响应体的媒体类型，部分类型可指定字符集 | `text/html; charset=utf-8`、`application/json`、`image/png` |
| `Content-Length` | 声明消息内容的字节数 | `2048`；有内容压缩时对应压缩后的内容字节数，不含头部及分块等传输开销；`HEAD` 等场景另有语义 |
| `Content-Encoding` | 声明内容采用的编码，客户端据此解码 | `gzip`、`br`；与 `Content-Type` 的含义不同 |
| `Content-Language` | 表示内容面向的受众语言 | `zh-CN`、`en` |
| `Content-Disposition` | 提示浏览器如何呈现内容，并可提供下载文件名 | `attachment; filename="report.pdf"`；`inline` 表示内联处理；中文等文件名常用 `filename*=UTF-8''...` |
| `Location` | 指定重定向目标，或新创建资源的位置 | `/login`；常配合 `301`、`302`、`303`、`307`、`308` 或 `201` |
| `Set-Cookie` | 设置、更新或删除浏览器 Cookie | `sessionId=abc123; Path=/; HttpOnly; Secure; SameSite=Lax`；多个 Cookie 应分别使用多条该头，不能用逗号简单合并 |
| `WWW-Authenticate` | 告诉客户端认证方案及相关参数 | `Bearer realm="api"`；服务器返回 `401 Unauthorized` 时应包含适用的认证挑战 |
| `Allow` | 声明目标资源支持的 HTTP 方法 | `GET, HEAD, POST`；返回 `405 Method Not Allowed` 时必须包含；它不是 CORS 的 `Access-Control-Allow-Methods` |
| `Retry-After` | 提示客户端等待多久再重试，可使用秒数或 HTTP 日期 | `120`；常配合 `429 Too Many Requests`、`503 Service Unavailable` |
| `Accept-Ranges` | 表示服务器对该资源支持的范围单位 | `bytes`；没有该头不等于一定不支持范围请求 |
| `Content-Range` | 描述返回部分内容的范围和资源总长度 | `bytes 0-1023/8192`；常见于 `206 Partial Content`；`416` 可用 `bytes */8192` 表达总长度 |
| `Date` | 表示消息生成的时间 | `Wed, 21 Oct 2026 02:00:00 GMT`；HTTP 日期使用 GMT |
| `Server` | 描述服务器软件 | `nginx`；具体暴露多少信息由服务器配置决定 |
| `X-Request-Id` | 常见的自定义请求标识，方便关联前后端日志 | `req-20261021-001`；无统一格式，也可能作为请求头发送；跨源读取时需暴露该响应头 |

下载行为可参考 [MDN：Content-Disposition](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Disposition)，长度语义见 [RFC 9110：Content-Length](https://www.rfc-editor.org/rfc/rfc9110.html#section-8.6)。

### 缓存相关

| 响应头 | 作用 | 示例／注意事项 |
| --- | --- | --- |
| `Cache-Control` | 指定缓存存储和复用规则，是现代 HTTP 缓存的主要控制字段 | `public, max-age=3600`、`private, no-cache`、`no-store` |
| `Expires` | 指定响应的新鲜度到期时间 | `Wed, 21 Oct 2026 03:00:00 GMT`；有效的 `Cache-Control: max-age` 优先于它 |
| `ETag` | 服务器为资源的某个表示提供的校验标识，不要求一定是内容哈希 | `"v1"` 为强 ETag，`W/"v1"` 为弱 ETag；配合 `If-None-Match` 等条件头 |
| `Last-Modified` | 表示资源最后修改的时间 | `Wed, 21 Oct 2026 01:00:00 GMT`；配合 `If-Modified-Since`，时间通常只有秒级精度；ETag 可更精确地区分资源版本 |
| `Vary` | 指定选择缓存版本时还要比较哪些请求头 | `Accept-Encoding, Accept-Language`；已有其他值时应合并，而非覆盖 |
| `Age` | 表示缓存对响应年龄的估计，单位为秒 | `120`；不是“缓存还剩多少秒”，也不只是当前 CDN 节点存储了多久 |

常见 `Cache-Control` 响应指令：

| 指令 | 含义 |
| --- | --- |
| `max-age=3600` | 指定新鲜度寿命为 3600 秒；缓存复用时还要考虑响应年龄等因素 |
| `s-maxage=600` | 指定共享缓存的新鲜度寿命；对共享缓存优先于 `max-age`，不控制浏览器私有缓存 |
| `public` | 明确允许共享缓存存储；仍需结合其他缓存规则 |
| `private` | 只允许私有缓存存储，不允许 CDN 等共享缓存存储 |
| `no-cache` | 可以存储，但每次复用前必须向服务器验证；不是“完全不缓存” |
| `no-store` | 不允许存储本次响应；不会自动清除之前已经存储的副本 |
| `must-revalidate` | 响应过期后，复用前必须成功验证，不能仅因断网就直接使用过期副本 |
| `immutable` | 表示响应在新鲜期内不会变化，可减少额外验证；常用于文件名带内容哈希的静态资源 |

典型配合：首次返回 `ETag: "v1"`，再次请求携带 `If-None-Match: "v1"`；如果资源没有变化，服务器可返回不带响应体的 `304`，客户端复用缓存内容。如果新鲜度允许直接使用缓存，通常连这次验证请求都不需要发送。

缓存指令可参考 [MDN：Cache-Control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control)；缓存年龄、验证和 `Vary` 的规则见 [RFC 9111：HTTP Caching](https://www.rfc-editor.org/rfc/rfc9111.html)。

## Cookie 与 Set-Cookie 的区别

- `Set-Cookie` 是服务器设置 Cookie 的响应头；`Cookie` 是客户端后续请求携带 Cookie 键值对的请求头。
- `HttpOnly` 禁止网页 JavaScript 通过 `document.cookie` 等方式访问该 Cookie，但不会阻止浏览器在符合规则的请求中自动携带它。
- `Secure` 限制 Cookie 通过安全连接发送；`SameSite` 控制跨站发送条件；`Domain`、`Path` 控制作用范围。
- `Max-Age`、`Expires` 控制 Cookie 的有效期，同时设置时 `Max-Age` 优先；这些是 `Set-Cookie` 的属性，不是需要跟着 `Cookie` 请求头一起发回去的字段。
- `SameSite=None` 需要配合 `Secure`；正确配置仍可能受浏览器的第三方 Cookie 策略影响。

Cookie 的设置与发送规则见 [MDN：Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)。

## 常见安全响应头

这些头作用于不同的浏览器安全机制，不用于代替 CORS 的允许来源配置。

| 响应头 | 作用 | 示例／注意事项 |
| --- | --- | --- |
| `Content-Security-Policy` | 限制页面允许加载、执行的资源及其他行为，帮助降低 XSS 等风险 | `default-src 'self'; object-src 'none'; frame-ancestors 'self'`；具体策略需要结合页面资源配置 |
| `Strict-Transport-Security` | 要求浏览器在有效期内使用 HTTPS 访问该主机 | `max-age=31536000`；只在 HTTPS 响应中被接受；`includeSubDomains` 会把策略扩展到子域 |
| `X-Content-Type-Options` | 要求浏览器按声明的媒体类型处理内容，阻止部分 MIME 类型嗅探行为 | `nosniff`；仍需正确设置 `Content-Type` |
| `X-Frame-Options` | 控制页面是否允许被框架嵌入，帮助防范点击劫持 | `DENY` 或 `SAMEORIGIN`；CSP 的 `frame-ancestors` 可表达更灵活的嵌入策略 |
| `Referrer-Policy` | 控制后续请求中 `Referer` 的发送范围 | `strict-origin-when-cross-origin`：同源可带路径，跨源通常只带源，从 HTTPS 降级到 HTTP 时不发送 |
| `Permissions-Policy` | 控制页面及其嵌入内容使用特定浏览器功能的权限 | `camera=(), microphone=()`：禁用摄像头、麦克风；字段语法与 CSP 不同 |

页面资源策略见 [MDN：CSP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy)，HTTPS 策略见 [MDN：HSTS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Strict-Transport-Security)；来源信息与功能权限分别见 [MDN：Referrer-Policy](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Referrer-Policy) 和 [MDN：Permissions-Policy](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Permissions-Policy)。

## 连接与代理中常见的头

| 头字段 | 常见方向 | 作用／注意事项 |
| --- | --- | --- |
| `Connection` | 请求／响应 | HTTP/1.x 中指定连接选项，如 `close`；HTTP/1.1 默认支持持久连接，不需要为此强行添加 `keep-alive` |
| `Keep-Alive` | 请求／响应 | 部分 HTTP/1.x 连接中用于描述超时、最大请求数等参数；不能与 TCP keepalive 或 Fetch 的 `keepalive` 选项混为一谈 |
| `Transfer-Encoding` | 请求／响应 | HTTP/1.1 中描述传输编码，如 `chunked`；不同于内容压缩的 `Content-Encoding` |
| `Forwarded` | 请求，代理追加 | 标准代理转发信息，例如 `for=192.0.2.10;proto=https;host=api.example.com` |
| `X-Forwarded-For` | 请求，代理追加 | 常见的非标准客户端／代理地址链；只有来自可信代理、按正确规则处理的值才能用来识别客户端 IP |
| `X-Forwarded-Proto` | 请求，代理追加 | 表示客户端连接到代理时使用的原始协议，如 `https`；同样需要可信代理配置 |

`Connection`、`Keep-Alive`、`Transfer-Encoding` 等连接专用字段不能照搬到 HTTP/2、HTTP/3；现代协议使用自己的连接与数据帧机制。相关区别可参考 [MDN：Connection](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Connection)。

代理转发字段可参考 [MDN：Forwarded](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Forwarded) 和 [X-Forwarded-For](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/X-Forwarded-For)。
