检查越权的核心是：**服务端认定你是谁，以及你是否有权操作请求指向的数据。**

## 举例
我选你表格里的 **`UserController.update`：`POST /user/update`** 举例。

检查当前代码后，我的判断是：**显式传入他人的 `id` 会被拦截，但表格里的“无越权风险”还需要补充验证。** 本次是静态检查，没有实际调用接口修改数据。

检查越权的核心是：**服务端认定你是谁，以及你是否有权操作请求指向的数据。** 对这个接口，预期规则是“用户只能修改自己的资料”。[OWASP 检查原则](https://cheatsheetseries.owasp.org/cheatsheets/Insecure_Direct_Object_Reference_Prevention_Cheat_Sheet.html)

**1．先找到身份、目标和权限判断**

打开 [UserController.java (line 164)](/D:/workspace/wh/wt/wt-web/src/main/java/com/wotransfer/web/payer/controller/UserController.java:164)，关键代码是：

```java
TokenInput tokenInput = TokenInputUtil.getTokenInputObj(request);

if (tokenInput == null ||
    (users.getId() != null && tokenInput.getUserId() != users.getId())) {
    return ResultRich.newInstance(ErrorCode.LOGIN_EXPIRED);
}

// 省略姓名字段处理
return UserConvertPayerV2.toPayerV2Result(payerClient.userUpdate(users));
```

这里：

- `tokenInput.getUserId()`：服务端使用的当前登录用户身份。
- `users.getId()`：客户端传入的待修改用户。
- 二者不同就返回，而且返回发生在调用更新服务之前。

例如：甲的用户 ID 是 `1001`，乙是 `1002`。甲登录后提交 `{"id":1002,...}`，比较结果不相等，会进入拒绝分支。这就是检查**水平越权**的典型场景。

**2．继续检查条件的边界和下游**

注意这个条件：

```
users.getId() != null && ...
```

如果请求不传 `id`，或传 `"id": null`，就会跳过 ID 比较。当前方法也没有把 `id` 补成登录用户，而是继续把 `users` 传给下游。

沿着 [PayerClient.userUpdate (line 158)](/D:/workspace/wh/wt/wt-web/src/main/java/com/wotransfer/web/client/PayerClient.java:158) 追踪，实际更新由 `service-payer` 的 `/payer/v2/user/update` 完成。因此还要确认：

- 下游遇到空 `id` 会拒绝，还是通过其他字段定位用户？
- 如果能通过 `email`、`userId` 等字段定位，是否仍限制为当前登录用户？
- 最终实际修改的用户，是否就是权限校验通过的那个用户？

**空 ID 跳过比较是已确认的代码行为；是否能因此修改他人，需要下游代码或运行结果证明。**

**3．确认“登录身份”真的可信**

我还查看了本机缓存的 `core` 依赖：`getTokenInputObj()` 会读取请求属性 `tokenObj`，没有该属性时，会尝试解析同名请求头。这一步本身没有展示登录 token 的验证。

所以需要继续检查实际部署的网关：

- 是否先验证登录 token，再生成 `tokenObj`？
- 是否删除或覆盖客户端自带的 `tokenObj`？
- 外部请求是否都经过这条认证链路？

否则，即使两个 ID 相等，也可能只是比较了两份客户端可控的数据。本机依赖的行为还应与实际部署版本核对。
